拆 Claude Code 的 system prompt

L04 说系统提示词是"控制面板"——今天打开 CC 真实 system prompt，验证这件事。

← 上一课：系统提示词层 模块测验 01 →
数据来源

本课所有数字、分段名、token 计数来自 Piebald-AI/claude-code-system-prompts 仓库，对应 Claude Code v2.1.220（2026-07-24）。该仓库从 CC 编译产物里抽取真实 prompt 字符串，与 CC 实际使用的完全一致。

第一个惊讶：CC 没有"一个" system prompt

你可能以为 system prompt 是一段写在某处的长文本。打开 CC 的实现，第一个反直觉的事实：

Piebald 仓库的开场白

"Claude Code doesn't just have one single string for its system prompt." CC 的 system prompt 不是单一字符串，而是 515 段（2026-06 从 350 段扩到 515）被拼起来、且大量段落是条件注入的——按环境和配置决定哪些段进、哪些不进。

这 515 段分四大类：

类别是什么举例
① 主 system prompt塑造主 agent 行为的指令段（本身由几十个 fragment 拼成）身份、工具使用原则、安全、语气…
② 内建工具描述27 个工具各自的描述（喂给模型的 tool definition）Write / Bash / TodoWrite / Read…
③ 子 agent prompt内建子 agent 各自的 system promptExplore（871 tks）、Plan（715 tks）
④ 工具型 promptAI 驱动的辅助功能各自的 prompt对话压缩、CLAUDE.md 生成、会话标题…

注意②：工具描述在 L06 会讲——它本质也是"喂给模型的文本"，和系统提示词同源。CC 把它单列是因为有些工具描述很大（如 Bash、Tool use concepts）。

第二个惊讶：主 prompt 内部是一堆"小片段"，每段调一层

真正印证 L04"控制面板"视角的，是主 system prompt 的内部结构。它不是一整段散文，而是几十个命名 fragment，每个 fragment 调一个具体行为/一层 harness。从 Piebald 抽的片段名和 token 数：

fragment（CC 内部名）tks调的是哪层 / 什么行为
Tool use concepts11835工具层——何时该用工具、怎么选工具的总纲（最大一段）
Coordinator mode orchestration5916编排层——多 agent 协调、派发子任务
Executing actions with care1105权限/安全层——危险操作要确认、谨慎执行
Delivering work at full scope605任务收口——交付完整范围、别半途而废
Context compaction summary409上下文层——压缩时怎么生成摘要
Correction restraint365别过度纠正用户、别画蛇添足
Communication style297输出格式/语气
Censoring assistance with malicious activities98安全层——拒绝恶意请求
Doing tasks (no unnecessary additions)73防过度工程——不加要求外的东西
Doing tasks (no unnecessary error handling)64防过度工程——不为不可能场景写错误处理

L04 的论断，被实证了

L04 说"系统提示词是 harness 各层的控制面板"。看 CC 的真实 fragment 表：工具层、编排层、权限安全层、上下文层、防过度工程——每一层都对应一个或几个 prompt 片段在调控。这不是比喻，是 CC 的工程现实。很多你以为要"改代码"才能调的行为，其实是在 system prompt 里改一句话。

第三个惊讶：你和 CC 想到一起去了

看这条 fragment：

Doing tasks (no unnecessary additions)  // 73 tokens
Doing tasks (no unnecessary error handling) // 64 tokens

这是 CC 内部防过度工程的 prompt 片段。现在翻翻你自己的 CLAUDE.md：

没有要求的功能就不做。
单次使用的代码不要抽象。
没有要求的"灵活性""可配置性"不要加。
不可能发生的场景不要写错误处理。

几乎一模一样。你不是在"学习一个新概念"——你已经在用 CC 同款的思路写系统提示词了，只是规模小、放在 CLAUDE.md 这个用户入口里。CC 的 system prompt 就是工业级、碎片化、条件注入版的 CLAUDE.md。

为什么是 500+ 段而不是一段？条件注入

Piebald 仓库解释了为什么 CC 的 prompt 碎成这么多段："Large portions conditionally added depending on the environment and various configs." 不同段落按环境/配置动态拼接。真实例子：

  • 按语言注入：只有当仓库含该语言时，才注入 Tool use reference — Python（7076 tks）/ TypeScript（7559 tks）/ Go（3468 tks）等。不会一股脑全塞——省 token、减干扰。
  • 按模式注入：Autonomous loop tick、Autonomous operation guidelines 等片段只在 /loop 自主模式下注入。
  • 按能力注入：Chrome browser MCP tools、Claude in Chrome browser automation 只在浏览器 MCP 接入时注入。
这就是上下文工程

条件注入不是为了优雅，是上下文预算管理——系统提示词也占 context window，全塞进去既贵又稀释注意力。CC 按需注入，是 L09 上下文管理层的提前预演。系统提示词层和上下文层在这里交汇。

定制入口：你想"读透并定制"，从哪下手

你的 mission 之一是"读透现有 harness 并尝试定制"。CC 的 system prompt 层有两个定制入口，投入产出比从高到低：

入口改什么难度持久性
CLAUDE.md用户层注入——追加你自己的指令片段（CC 启动时拼进 system prompt）低（写 markdown）跨版本存活（你的文件，CC 升级不动它）
tweakcc改 CC 内部 fragment 本身——把任一段导出为 markdown，改完 patch 回 CC 安装中（需理解片段含义）CC 升级可能冲突，需 diff 管理

tweakcc 来自 Piebald 团队，专门把 CC 的 minified prompt 拆成可编辑 markdown，并提供冲突管理——正好对上"读透并定制"的目标。模块 7 定制实战（L20-L23）会动手。

售前提醒

客户要"定制 agent 行为"，先问能不能用 CLAUDE.md 解决——一句话注入就能改行为，零维护成本。只有 CLAUDE.md 表达不了的深度定制（改工具调度逻辑、改压缩策略）才考虑 tweakcc 或自建 harness。这是售前投入产出比的第一判断。

本课小结

  • CC 的 system prompt 不是一段，是 515 段条件注入，分四类（主 prompt / 27 工具描述 / 子 agent / 工具型）。
  • 主 prompt 内部是每段调一层的 fragment——工具/编排/权限/上下文/防过度工程都有对应片段。L04"控制面板"论断被实证。
  • 你的 CLAUDE.md 和 CC 内部 fragment（如 Doing tasks (no unnecessary additions)）同款思路，只是用户层入口。
  • 定制入口：CLAUDE.md（低本高回报）→ tweakcc（深度定制，需维护）。

1Claude Code 的 system prompt 是怎样的结构？

✓515 段条件注入的片段，按环境/配置动态拼成
✓一段写在配置文件里的长文本
✓完全由模型自己生成
✓只有 CLAUDE.md 这一段
答案：515 段条件注入。
  • 515 段条件注入 ✓：Piebald 仓库原话"doesn't just have one single string"，515 段按环境/配置动态拼接。
  • 一段长文本 ✗：这正是反直觉点——它不是单段，是碎片化条件注入。
  • 模型自己生成 ✗：system prompt 是 harness 侧注入的，不是模型生成的。
  • 只有 CLAUDE.md ✗：CLAUDE.md 只是用户层注入的一段，主 prompt 还包含工具原则/安全/编排等几十段。
口诀：「CC prompt 不是一段，是五百段条件装」——条件注入省 token、减干扰。

2CC 内部 fragment Executing actions with care（1105 tks）调的是哪一层？

✓权限/安全层（危险操作要确认）
✓工具层（怎么调工具）
✓上下文层（窗口压缩）
✓编排层（多 agent 派发）
答案：权限/安全层。
  • 权限/安全层 ✓："executing actions with care"=谨慎执行操作，对应危险操作前确认、谨慎执行，是安全层行为。
  • 工具层 ✗：工具层由 Tool use concepts（11835 tks）那段调，不是这段。
  • 上下文层 ✗：上下文层由 Context compaction summary（409 tks）调。
  • 编排层 ✗：编排层由 Coordinator mode orchestration（5916 tks）调。
口诀：「看片段名认层」——care=安全、concepts=工具、orchestration=编排、compaction=上下文。

3售前场景：客户想改 CC 一个具体行为（比如"改代码前先读文件"），投入产出比最高的第一步是？

✓先写进 CLAUDE.md 试一句话注入
✓直接用 tweakcc 改 CC 内部 fragment
✓自建一套 harness 从头实现
✓改 Claude Code 源码重新编译
答案：先写进 CLAUDE.md。
  • 先 CLAUDE.md ✓：CC 启动时把 CLAUDE.md 拼进 system prompt，一句话就能改行为，零维护、跨版本存活——投入产出比最高。
  • 直接 tweakcc ✗：能做但不是第一步。tweakcc 改内部 fragment，CC 升级可能冲突，需 diff 管理。只有 CLAUDE.md 表达不了时才上。
  • 自建 harness ✗：过度方案。一句话能解决的事不值得自建。
  • 改源码重编译 ✗：最重方案，且 CC 闭源/升级即丢，售前绝不从这里开始。
口诀:「定制先 CLAUDE.md，不够再 tweakcc，最后才自建」——从轻到重。

4为什么 CC 把 prompt 碎成 500+ 段条件注入，而不是一段全塞？

✓按需注入省 context 预算、减干扰
✓因为模型一次只能处理 500 字
✓为了让 README 看起来长
✓法律要求必须分段
答案：按需注入省预算、减干扰。
  • 按需注入省预算 ✓：system prompt 占 context window，全塞既贵又稀释注意力。按语言/模式/能力条件注入，是上下文工程。
  • 模型只能处理 500 字 ✗：模型上下文窗口远大于此，碎段不是因为处理不了，是为了精准和省钱。
  • README 显长 ✗：无关。这是 CC 运行时的工程决策，不是文档展示。
  • 法律要求 ✗：无此要求。纯属工程权衡。
口诀:「条件注入=上下文预算管理」——系统提示词层和上下文层在这里交汇（L09 展开）。
