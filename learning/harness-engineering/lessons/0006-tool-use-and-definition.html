从 L02 的黑盒说起

L02 的 while 循环里，工具是个黑盒：你传了 tools=[...]，模型"调用"了，你 run_tool 执行了，结果喂回去。但工具定义长什么样？模型是真的在"调用函数"吗？这两个问题不弄清，售前给客户讲"我们能给 agent 加工具"就讲不踏实。

一、什么是工具：确定 × 非确定的契约

Anthropic 在 Writing effective tools 里给了个精准定位：

原文要义

传统软件是确定性系统之间的契约——getWeather("NYC") 每次都以完全一样的方式拿天气。而工具是确定性系统 × 非确定性 agent 的新契约：用户问"今天要带伞吗"，agent 可能调天气工具、可能直接用知识答、可能先问你在哪个城市，偶尔还会幻觉或不会用。

这带来一个根本转变：工具不是给开发者用的 API，是给 agent 用的。不能按写函数/API 的方式写，要按 agent 的认知方式设计。这条伏笔 L07 展开（怎么选工具、怎么写描述），今天先把机制和定义讲透。

二、工具定义解剖：三要素

一个工具定义就是三块：name / description / input_schema。真实的 get_weather 长这样：

{
  "name": "get_weather",
  "description": "获取指定城市的当前天气。",
  "input_schema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "城市名，如 'NYC'"
      }
    },
    "required": ["location"]
  }
}
要素作用注意
name工具名，agent 靠它选工具要无歧义；多工具时要 namespacing（L07）
description给 agent 看的说明会被拼进 system prompt——见第五节
input_schema参数的 JSON Schema类型 / required / enum 约束取值

三、模型怎么"调"工具：它不调，它"说"

这是本课最反直觉的一点：模型不会真的执行函数。它做的，是输出一个 tool_use 块（结构化文本）：

{
  "type": "tool_use",
  "name": "get_weather",
  "input": {"location": "NYC"},
  "id": "toolu_01abc"
}

真正的执行在 harness 侧的 run_tool——就是你 L02 写的那个函数。模型只是"说"它想调什么、参数是什么，harness 替它跑。这正好回答了 Q&A Q1：run_tool 是 harness 侧的代码，不是模型内部的东西。

为什么是这样设计

模型是个文本输入/文本输出的推理机，它没有执行代码的能力。能跑代码的是你（harness）。所以"工具调用"本质是：模型用结构化文本表达意图，harness 解析并执行。这个分工是 L02 那个 while 能转起来的根。

四、调用协议：tool_use ↔ tool_result 配对

把 L02 的循环展开成时序，看 tool_use 和 tool_result 怎么靠 id 串起来：

1
模型输出 assistant 消息，含 tool_use 块（name / input / id），stop_reason="tool_use"
↓
2
harness 解析 tool_use，调 run_tool(name, input)，拿到结果
↓
3
harness 构造 user 消息，含 tool_result 块（tool_use_id 对上 / content），喂回模型
↓
4
模型读 result，决定：继续调工具（回到 1）or end_turn 停下

配对靠 tool_use_id——assistant 的 tool_use.id 和 user 的 tool_result.tool_use_id 必须一致。一条 assistant 消息可以含多个 tool_use 块（并行调用多个工具），每个都对应一个 tool_result。

API 无状态的后果

Messages API 是无状态的——每次 messages.create 都要把完整历史发过去（Q&A Q2）。所以 tool_use 和 tool_result 作为历史消息一直留在 messages 里，模型每轮都重读。这也是为什么工具结果太大会吃爆 context——L09 展开。

五、工具描述也是系统提示词（控制面板延伸）

看 description 字段——它不只是文档，Anthropic 文档明说：工具定义被 dynamically loaded into Claude's system prompt。Writing effective tools 也强调描述 "are loaded into your agents' context"。

L05 控制面板，在工具层的延续

L05 说 CC 的 system prompt 里有 Tool use concepts（11835 tks）这种大片段调工具层。现在你明白了：每个工具的 description 也是拼进 system prompt 的一部分。你写工具描述 = 在调工具层行为。所以"写好工具描述"本质是 prompt 工程——L07 专门讲。

六、参数设计速览（深在 L07）

  • 无歧义命名：用 user_id 不要用 user——agent 不知道 user 该传名字还是 ID。Anthropic 原话："input parameters should be unambiguously named"。
  • required 标必填：必填的放 required 数组，可选的不放。
  • enum 约束取值：取值固定时用 enum，如 response_format: ["concise","detailed"]，减少 agent 猜错。
  • 参数也要写 description：每个参数的 description 同样进 system prompt，是 prompt 工程的一部分。

本课小结

  • 工具 = 确定 × 非确定的契约，按 agent 认知设计，不是给开发者的 API。
  • 定义三要素：name / description / input_schema（JSON Schema）。
  • 模型不真调函数，输出 tool_use 块；harness 侧 run_tool 执行；tool_result 喂回，靠 id 配对。
  • description 被拼进 system prompt = 工具层的控制面板（L05 延伸）。怎么写好 → L07。

1用户问"今天要带伞吗"，模型决定调 get_weather。这一刻模型实际做了什么？机制

✓真的执行了 get_weather 函数，拿到天气数据
✓输出一个 tool_use 块（结构化文本），由 harness 侧的 run_tool 去执行
✓直接用自己训练时的知识回答，不调工具
✓生成一段调用日志写到磁盘
答案：输出 tool_use 块，harness 执行。
  • 真执行函数 ✗：模型是文本输入/输出推理机，没有执行代码的能力。能跑代码的是 harness。
  • 输出 tool_use 块 ✓：模型用结构化文本表达"我想调 get_weather，参数 location=NYC"，harness 解析后调 run_tool。这是"工具调用"的本质。
  • 直接用知识 ✗：agent 确实可能这么做（确定×非确定契约），但题目说"决定调 get_weather"，那就走工具路径，不是用知识答。
  • 写日志 ✗：无关，模型不写磁盘。
口诀:「模型说，harness 做」——tool_use 是意图，run_tool 是执行。

2一个工具定义由哪三要素组成？定义

✓name / description / output_schema
✓name / description / input_schema
✓name / version / dependencies
✓prompt / model / temperature
答案：name / description / input_schema。
  • output_schema ✗：易混点——工具定义的是输入参数 schema（input_schema），输出是 tool_result 自由格式内容，没有 output_schema 字段。
  • input_schema ✓：name 供 agent 选用，description 给 agent 说明（且拼进 system prompt），input_schema 是参数的 JSON Schema（类型/required/enum）。
  • version/dependencies ✗：这是软件包的概念，不是工具定义。
  • prompt/model/temperature ✗：这是调用参数，不是工具定义本身。
口诀:「工具三件套：名字、说明、参数表」——name 让 agent 选，description 让 agent 懂，input_schema 让参数对；输出没 schema。

3设计 send_message 工具时，参数该叫 user 还是 user_id？为什么？应用

✓user——更短，agent 更好记
✓user_id——无歧义，agent 不会纠结该传名字还是 ID
✓无所谓，agent 都能猜对
✓u——最省 token
答案：user_id。
  • user ✗：歧义——agent 不知道该传用户名、邮箱还是 ID，容易猜错。Anthropic 原话"input parameters should be unambiguously named"。
  • user_id ✓：明确告诉 agent 传 ID，消除歧义，减少参数错误。
  • 无所谓 ✗：命名对工具调用成功率影响很大，Sonnet 3.5 在 SWE-bench 上靠精修工具描述就大幅降错。
  • u ✗：省 token 但牺牲清晰度，agent 难理解，本末倒置。
口诀:「参数名要一眼懂，user_id 不含糊」——清晰优先于简短。

4给 agent 做通讯录工具，list_contacts（返回全部联系人）和 search_contacts（按名搜索）哪个更合适？决策

✓list_contacts——功能更全，agent 拿到全部数据自己挑
✓search_contacts——只返回相关结果，不浪费 agent 有限的 context
✓两个都做，让 agent 自己选
✓都不做，让 agent 用知识猜
答案：search_contacts。
  • list_contacts ✗：返回全部联系人，agent 要逐条读 token 浪费有限 context——像"从头到尾翻通讯录找人"。Anthropic 明确反对这种暴力遍历。
  • search_contacts ✓：只返回相关结果，把"找"的工作放回工具里，省 context、降出错率。这是"选对工具"的核心原则。
  • 两个都做 ✗：工具重叠会分散 agent 注意力，且 list 本身就是反模式。少而精更好。
  • 都不做 ✗：通讯录是私有数据，agent 训练时没见过，用知识猜必幻觉。
口诀:「agent 工具要跳到相关页，别从头翻」——search 优于 list，少而精优于多而全。
