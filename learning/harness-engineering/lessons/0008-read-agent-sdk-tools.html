读 Agent SDK 工具实现

L06 讲了 API 层的"工具三要素"，L07 讲了 5 设计原则。今天落到 Claude Agent SDK：真实的工具怎么定义、注册、调度、出错怎么办。

先说清一个真相：SDK 是 wrapper，不是源码

课程目录原本写"读源码怎么定义与调度工具"。我去看 claude-agent-sdk-typescript 仓库，根目录没有 src/——只有 README、examples、CHANGELOG。官方文档明说：SDK 是个 standalone 包，内嵌 Claude Code 的 agent loop，通过 spawn claude 进程（subprocess）跑。reddit 上开发者也证实："the agent SDK is basically a wrapper... spawns a claude process"。

调整策略：读文档 + 实例代码

loop 的实现源码不在这个仓库里（在 CLI 内部）。但工具的定义和调度接口是公开文档化的——tool() 函数、createSdkMcpServer、注解、权限两层、错误处理，官方 custom-tools 文档讲得透。这比读 wrapper 源码更准。所以本课读文档+实例，不假装读不到的源码。

一、从 API 三要素 到 SDK 四部分

L06 讲的 name / description / input_schema 是 Anthropic API 层模型看到的三要素。SDK 层多了两块——handler（真正执行的代码）和可选 annotations（行为注解）。官方原文："A tool is defined by four parts"：

部分作用对应 L06
Name唯一标识，Claude 靠它调用= name
DescriptionClaude 读它决定何时调用= description
Input schema参数；TS 用 Zod，Py 用 dict/JSON Schema= input_schema（SDK 自动转 JSON Schema）
Handlerasync 函数，Claude 调用时执行SDK 新增（API 层没有）
Annotations（可选）行为元数据（readOnlyHint 等）SDK 新增
为什么 SDK 多了 handler

API 层你只声明工具（model 看到三要素），执行靠你自己写 run_tool（L02）。SDK 把"声明 + 执行"打包：tool() 既定义 schema 又绑 handler，一个调用同时给模型看（schema）和替模型跑（handler）。这就是从"手写 loop"到"用 SDK"的核心简化。

二、tool() 函数解剖（TypeScript）

官方 weather 工具示例（原文 verbatim）：

import { tool, createSdkMcpServer } from "@anthropic-ai/claude-agent-sdk";
import { z } from "zod";

const getTemperature = tool(
  "get_temperature",                              // 1. name
  "Get the current temperature at a location",    // 2. description（Claude 读它决定何时调）
  {
    latitude: z.number().describe("Latitude coordinate"),   // 3. schema：Zod，.describe() 字段说明 Claude 可见
    longitude: z.number().describe("Longitude coordinate")
  },
  async (args) => {                                // 4. handler：args 自动从 schema 推断类型
    const response = await fetch(
      `https://api.open-meteo.com/v1/forecast?latitude=${args.latitude}&longitude=${args.longitude}¤t=temperature_2m&temperature_unit=fahrenheit`
    );
    const data: any = await response.json();
    return {                                        // 返回 content 数组（MCP 格式）
      content: [{ type: "text", text: `Temperature: ${data.current.temperature_2m}°F` }]
    };
  }
);

三个 Zod 技巧（对应 L06/L07 讲的参数设计）：

  • .describe()：给字段加说明，这个说明 Claude 也能看到（进 system prompt）——L07 原则 5 的落点。
  • .default(12)：让参数可选（带默认值）。
  • z.enum(["length","temperature","weight"])：约束取值——L06 讲的 enum，这里落地。
Zod 的类型推断

handler 的 args 不用手动声明类型——Zod schema 自动推断。你写 latitude: z.number()，args.latitude 就是 number。改 schema 类型，handler 类型自动跟。这是 TS 版 SDK 的核心人体工学优势。

三、注册：从 tool 到 mcp__server__tool

定义完工具，要包成 MCP server 再传给 query()。三步：

1
定义：tool() 造工具（上面的 getTemperature）
↓
2
包成 server：createSdkMcpServer({name:"weather", version:"1.0.0", tools:[getTemperature]})——in-process，不单独进程
↓
3
传给 query：query({prompt, options:{mcpServers:{weather: weatherServer}, allowedTools:["mcp__weather__get_temperature"]}})

工具全名格式（关键）：MCP 工具暴露给 Claude 时叫 mcp__{server_name}__{tool_name}。weather server 里的 get_temperature → mcp__weather__get_temperature。这个全名要写进 allowedTools 才免权限提示。

server 名 = 命名空间

发现没？mcp__weather__get_temperature 里的 weather 就是 L07 原则 2 讲的 namespacing——SDK 用 server 名自动做前缀分组。不同 server 的同名工具不会撞：weather 的 search 和 jira 的 search 分别是 mcp__weather__search / mcp__jira__search。原则 2 在 SDK 层是强制的。

多工具用通配符：allowedTools: ["mcp__weather__*"] 一次批准整个 server。

四、内置工具 + tool search

SDK 自带 CC 同款内置工具（Read/Glob/Grep/Edit/Write/Bash 等），开箱即用。自定义工具走 MCP server 接入。

tool search 默认开：MCP 工具 schema 延迟加载——Claude 先看到一个紧凑工具名列表，用到时才加载完整 schema。好处是省 context（几十个工具不全量塞进每轮 prompt）。坏处是可能多一次 ToolSearch 调用。想强制全 schema 进初始 prompt？alwaysLoad: true。

衔接 L09 上下文层

tool search 是"工具定义吃 context"这个问题的解法——和 L09 要讲的 context 管理、压缩是一脉。先记住：工具越多，schema 占 context 越多，tool search 用延迟加载缓解。

五、并行 vs 串行：readOnlyHint

Claude 一轮可以请求多个工具调用。SDK 怎么调度？看工具改不改状态：

工具类型调度例子
只读（标记 readOnlyHint）并行Read / Glob / Grep / MCP 只读工具
写/改状态串行Edit / Write / Bash
自定义工具（默认）串行不设注解的自定义 tool

自定义工具默认串行。想并行？第五参数设 readOnlyHint: true：

tool(
  "get_temperature",
  "Get the current temperature at a location",
  { latitude: z.number(), longitude: z.number() },
  async (args) => ({ content: [{ type: "text", text: `...` }] }),
  { annotations: { readOnlyHint: true } }    // 第五参数：让 Claude 把它和其他只读工具并行调
);

四类注解（官方表）：

Field默认含义是否强制
readOnlyHintfalse不改环境；控制能否并行影响调度
destructiveHinttrue可能破坏性更新仅信息
idempotentHintfalse重复调用无额外效果仅信息
openWorldHinttrue访问进程外系统仅信息
注解是元数据，不是强制

官方原文："Annotations are metadata, not enforcement. A tool marked readOnlyHint: true can still write to disk if that's what the handler does."——注解要和 handler 实际行为一致。标了只读但 handler 写盘，调度会误并行，可能出竞态。诚实标注。

六、可用性 vs 权限：两层区分（易混点）

工具控制有两个独立层，官方原文明确区分：

选项层效果
tools: ["Read","Grep"]可用性只有列出的内置工具出现在 context；未列的移除
tools: []可用性所有内置移除，Claude 只能用你的 MCP 工具
allowedTools权限列出的免提示直接跑；未列的仍在 context 但走权限流
disallowedTools 裸名（"Bash"）两层从 context 移除（Claude 看不见）
disallowedTools 带范围（"Bash(rm *)"）两层留在 context 但拒绝匹配调用（Claude 可能浪费一轮试）
关键区分

可用性（tools / 裸名 disallowedTools）= Claude 看得见什么工具。权限（allowedTools / scoped disallowedTools）= Claude 调了让不让跑。想让 Claude 完全不知道有 Bash？用 tools 不列它，或 disallowedTools:["Bash"]。只想拦 rm 但留 Bash 可用？disallowedTools:["Bash(rm *)"]。这层区分是 L12 权限层的伏笔。

七、错误处理：不中断 loop（验证 L07）

L07 讲了"错误作为 tool_result 喂回，不中断 loop"。看 SDK 官方怎么实现——原文："A handler error doesn't stop the agent loop."。两种出错路径：

情况Claude 看到什么
handler 抛未捕获异常MCP server 转成 error result，带原始异常消息，loop 继续
handler 捕获并返回 isError: true你组装的消息（可加上下文/建议），loop 继续

两种情况 Claude 都能重试 / 换工具 / 解释失败。官方 fetch_data 示例（捕获后组装可操作错误）：

async (args) => {
  try {
    const response = await fetch(args.endpoint);
    if (!response.ok) {
      return {                              // 失败也作为 tool_result 返回
        content: [{ type: "text", text: `API error: ${response.status} ${response.statusText}` }],
        isError: true                        // 标记失败，Claude 知道这不是数据
      };
    }
    const data = await response.json();
    return { content: [{ type: "text", text: JSON.stringify(data, null, 2) }] };
  } catch (error) {
    return {                                  // 网络错误也组装成可操作消息
      content: [{ type: "text", text: `Failed to fetch data: ${error instanceof Error ? error.message : String(error)}` }],
      isError: true
    };
  }
}
L07 原则在 SDK 层的实证

L07 说"错误要可操作，别给 opaque code"。SDK 官方示例正是这么做的：不抛 ERROR 500，返回 isError:true + 人话消息。原始异常消息往往不够 Claude 行动（"EINVAL"），你自己 catch 就能加上"哪个请求失败、该试什么"。这就是 L07 原则 4"错误要可操作"在实现层的标准做法。

八、返回内容：不止 text

handler 的 content 数组每项有 type，可混合：

  • text：文本（最常用）
  • image：base64 内联图片（无 URL 字段，要 fetch 后编码）——Claude 当视觉输入
  • resource：带 URI 的内容块（URI 是标签，SDK 不真读那个路径，内容在 text/blob 字段）
  • structuredContent（可选，和 content 平级）：机器可读 JSON，Claude 读精确字段而非解析文本

structuredContent 适合"既要给人看（图）又要给模型读（数据）"：同一 handler 返回图表 image + 数据点 JSON，Claude 能精确引用 points 字段。

本课小结

  • SDK 是 wrapper：loop 实现在 CLI subprocess，仓库无 src；工具接口在官方文档，比源码更准。
  • 四部分定义：name / description / schema / handler（+ 可选 annotations）。比 API 三要素多 handler 和注解——声明+执行打包。
  • tool()：TS 用 Zod schema 自动类型推断；.describe() 字段说明进 prompt，.default() 可选，z.enum() 约束。
  • 注册三步：tool() → createSdkMcpServer → query(mcpServers)；全名 mcp__{server}__{tool}（server 名 = 强制 namespacing）。
  • tool search：默认延迟加载 MCP 工具 schema 省 context；alwaysLoad:true 强制全载。
  • 并行控制：只读并行、写串行；自定义默认串行，readOnlyHint:true 开并行。注解是元数据不是强制，要和 handler 一致。
  • 可用性 vs 权限两层：tools/裸名 disallow 控可见性；allowedTools/scoped disallow 控执行权。
  • 错误不中断 loop：未捕获→原始异常消息；捕获→isError:true+你组装的可操作消息。L07 原则的实证。
小胜利

你现在能用 Agent SDK 给 agent 加自定义工具了：写 tool() 定义 schema+handler，createSdkMcpServer 包好，query(mcpServers, allowedTools) 跑起来。而且知道每个旋钮调的是哪层：注解调调度、tools 调可见性、allowedTools 调权限、isError 调错误反馈。这是 L20 CC 定制实战的核心技能——给客户搭 agent 就是这套。

1用 Claude Agent SDK (TypeScript) 定义工具时，tool() 接收几部分？比 L06 讲的"API 三要素"多了什么？定义

✓三部分：name / description / input_schema（和 API 层一样）
✓四部分 + 可选注解：name / description / schema / handler（+ annotations）
✓两部分：name 和 handler，schema 自动生成
✓五部分都是必填：name / description / schema / handler / annotations
答案：四部分 + 可选注解。
  • 三部分 ✗：这是 L06 讲的 API 层模型看到的（name/description/input_schema）。SDK 层多了 handler——真正执行的 async 函数。API 层你只声明工具，执行靠手写 run_tool；SDK 把声明+执行打包。
  • 四部分 + 可选注解 ✓：官方原文"A tool is defined by four parts"——name / description / input schema / handler。annotations 是第五个可选参数（如 readOnlyHint）。
  • 两部分 ✗：schema 不会自动生成，要你用 Zod 写（TS）或 dict/JSON Schema（Py）。handler 也绑不了 schema。
  • 五部分都必填 ✗：annotations 是可选的（官方原话"optional metadata"），不设也有默认值（readOnlyHint=false 等）。
口诀:「API 三要素，SDK 四部分」——多了 handler（执行）+ 可选 annotations（行为注解）。

2你在 weather server 里定义了 get_temperature 工具，要让它免权限提示运行，allowedTools 里该写什么？应用 · 命名

✓"get_temperature"
✓"mcp__weather__get_temperature"
✓"weather.get_temperature"
✓"weather/get_temperature"
答案：mcp__weather__get_temperature。
  • get_temperature ✗：漏了 server 名前缀。MCP 工具暴露给 Claude 时用全名 mcp__{server}__{tool}，bare name 只对内置工具（Read/Bash）有效。
  • mcp__weather__get_temperature ✓：官方规定的全名格式——mcp__ 前缀 + server 名 weather + 工具名 get_temperature，双下划线分隔。allowedTools 要写全名才匹配。
  • weather.get_temperature ✗：点分格式不是 SDK 命名规范。也可用通配 mcp__weather__* 批量批准整个 server。
  • weather/get_temperature ✗：斜杠格式同样不对。记住是双下划线 __ 不是别的分隔符。
口诀:「MCP 工具全名三段：mcp__server__tool」——server 名就是 L07 的 namespacing，SDK 强制做前缀分组。

3你写了两个自定义只读工具（查库存、查价格），希望 Claude 一轮里并行调用它们省时间。该怎么做？机制

✓什么都不用做，自定义工具默认并行
✓给两个工具都设 annotations: { readOnlyHint: true }
✓在 query() 里加 parallel: true 选项
✓把两个工具放进不同的 MCP server
答案：设 readOnlyHint: true。
  • 默认并行 ✗：自定义工具默认串行（官方原文"Custom tools default to sequential execution"）。只有标了 readOnlyHint 的才并行。
  • readOnlyHint: true ✓：第五参数 annotations 里设 readOnlyHint:true，SDK 知道这工具不改状态，可和其他只读工具并行调。内置 Read/Glob/Grep 也靠这个机制并行。
  • parallel 选项 ✗：query() 没有 parallel 这个选项。并行性由工具自身的注解决定，不是全局开关。
  • 分不同 server ✗：server 分组和并行无关，只影响命名空间（mcp__A__x vs mcp__B__y）。同 server 的两个只读工具也能并行，关键看 readOnlyHint。
口诀:「自定义默认串行，readOnlyHint 开并行」——注解要诚实，标了只读就别在 handler 里写盘。

4handler 里调外部 API 抛了未捕获异常（比如网络断了）。agent loop 会怎样？机制 · 排错

✓整个 query() 立即崩溃，抛异常给调用方，agent 停止
✓MCP server 把异常转成 error result，Claude 看到原始异常消息，loop 继续转
✓SDK 自动重试该工具 3 次，全失败才停
✓静默吞掉异常，返回空结果给 Claude
答案：转成 error result，loop 继续。
  • 立即崩溃 ✗：官方原文明确"A handler error doesn't stop the agent loop"。SDK 的 in-process MCP server 捕获未捕获异常，转成 error result，不向上抛。
  • 转 error result 继续 ✓：MCP server 把异常转成带原始异常消息的 error result 喂回 Claude。Claude 能重试/换工具/告诉用户办不到。但原始异常消息往往不够行动（如"EINVAL"），所以最好自己 catch 返回 isError:true + 可操作消息（L07 原则 4）。
  • 自动重试 3 次 ✗：SDK 不会盲目重试工具。网络错误是瞬态的，但重试决策交给 Claude（它看到 error 后自己决定要不要再试），不是 SDK 层自动重试。
  • 静默吞掉 ✗：那 Claude 会以为成功、基于空结果继续，必出错。错误必须让 Claude 看见——SDK 这点设计正确，转成 error result 而非吞掉。
口诀:「handler 错不崩 loop，转 error result 喂回」——但原始消息不够行动，最好自己 catch 组装 isError。
