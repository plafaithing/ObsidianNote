写好工具——5 原则让工具从"能用"到"好用"

L06 讲透了机制和定义：循环能转，不代表转得好。工具是 agent 认识世界的唯一接口，工具烂则 agent 烂。今天讲怎么设计好。

核心心法：为 agent 设计，不是为开发者设计

L06 点过：工具是确定 × 非确定的契约。Anthropic 在 Writing effective tools 里把后果说得很直白：

原文要义

"instead of writing tools and MCP servers the way we'd write functions and APIs for other developers or systems, we need to design them for agents."——别按写函数/API 的方式写工具，要按 agent 的认知方式设计。

因为 agent 和传统软件的"affordance"不同：传统软件内存廉价，可以 list_contacts 返回全部逐条遍历；agent 的 context 金贵，逐条读 token 就是浪费生命。下面 5 条原则都从这条心法派生。

五条原则

1

选对工具粒度（Choosing the right tools）

反例：list_contacts 返回全部联系人，agent 逐条读——像"从头翻通讯录找人"，暴力遍历浪费 context。

正例：给 search_contacts（跳到相关页）。工具还能整合多步，把 agent 要调好几次的活一次干完：

# 选对粒度：让 agent 搜，别让 agent 翻
✗ list_contacts()                         # 返回全部，agent 逐条读
✓ search_contacts(name)                   # 只返匹配，省 context

# 整合多步：把 N 次调用压成 1 次
✗ list_users + list_events + create_event # agent 调 3 次自己拼
✓ schedule_event(attendees, when)         # 工具内部找空闲+建事件

✗ get_customer_by_id + list_transactions + list_notes  # 3 次
✓ get_customer_context(customer_id)       # 一次编译客户近期所有相关信息

为什么：agent context 有限，把"找"和"拼"的活放回工具里（确定性侧），省下 context 给推理。少而精，每个工具要有清晰独立的用途——工具重叠会分散 agent 注意力。

口诀:「让 agent 搜，别让 agent 翻；整合多步，少而精」
原文 "Choosing the right tools for agents"：search_contacts / schedule_event / get_customer_context 三例均出自此节。
2

命名空间分组（Namespacing）

agent 可能挂几十个 MCP server、几百个工具。工具功能重叠或目的模糊时，agent 会不知道调哪个。

# 按 service 前缀分组
✗  search / create / update               # Asana 和 Jira 都有 search，重名，agent 混
✓  asana_search / jira_search             # 按 service 前缀划开

# 再按 resource 细分
✓  asana_projects_search / asana_users_search

为什么：名字反映任务的天然划分，agent 选工具时更准，同时减少载入 context 的工具数和描述数。prefix 还是 suffix？原文说有"non-trivial effects"，看你自己评估选——没有绝对，但 Anthropic 示例都用 prefix。

口诀:「名前缀划边界，service + resource 分组」
原文 "Namespacing your tools"：asana_search / jira_search / asana_projects_search 例。
3

返回有意义上下文（Returning meaningful context）

工具返回的东西要直接能用在 agent 的下一步推理上，别返一堆底层技术标识符。

# 返名字，别返 UUID
✗  {"uuid":"4f3a...", "mime_type":"image/png", "256px_image_url":"..."}   # agent 还要再查才能用
✓  {"name":"架构图.png", "file_type":"png", "image_url":"..."}             # 直接能引用

# 兼顾两种需求：response_format 枚举
enum ResponseFormat { DETAILED="detailed", CONCISE="concise" }
# detailed: 返 ID（thread_ts/channel_id）供后续工具调用
# concise: 只返内容，约 1/3 token

为什么：agent 处理自然语言名远比处理 cryptic ID 强——原文说"merely resolving UUIDs to meaningful language significantly improves Claude's precision... by reducing hallucinations"。需要 ID 触发后续调用时，用 response_format 枚举让 agent 自选 detailed/concise。

口诀:「返名字不返 UUID，detailed/concise 让 agent 选」
原文 "Returning meaningful context"：uuid→name、ResponseFormat enum、Slack thread_ts 例。
4

token 效率（Optimizing for token efficiency）

不光返回的质量要高，数量也要控。可能吃爆 context 的工具，要带分页/范围/过滤/截断 + 合理默认值。

# CC 默认截断 25000 token
# 截断时给 agent 指引，别让它干等
"You returned 40000 tokens (truncated to 25000).
 Use 'filter' or 'page' to narrow results."

# 错误响应：可操作 vs 不可操作
✗  {"error": "EINVAL"}                    # agent 不知怎么改
✓  {"error": "customer_id 12345 not found.
       Try search_customers(name='acme') to find the correct ID."}

为什么：Claude Code 默认把工具响应截断到 25,000 token（原文明确数字）。截断了要引导 agent 用更省的策略（多而小的精准搜索 > 一次大搜索）。错误响应尤其要 prompt-engineer——给具体可操作的改进建议或正确格式示例，别给 opaque error code 或 traceback。

口诀:「默认截断 25000，截断给指引，错误要可操作」
原文 "Optimizing tool responses for token efficiency"：25,000 token 截断、truncated/error 响应示例。
5

prompt-engineer 描述（Prompt-engineering descriptions）

L06 点过：description 会被拼进 system prompt。所以写工具描述 = prompt 工程，是改善工具最有效的方法之一。

# 像给新员工解释，把隐含上下文写明
✗  description: "获取天气"
✓  description: "获取指定城市的当前天气。用于用户问天气/是否带伞/穿什么时调用。
                 location 传城市名如 'NYC'，不支持经纬度。
                 返回温度（摄氏）和天气状况。"

# 参数名无歧义（L06 已点，这里收口）
✗  {"user": "string"}        # 传名字？ID？邮箱？agent 猜
✓  {"user_id": "string"}     # 明确传 ID

为什么：像给团队新员工解释工具那样写——把你脑里隐含的（查询格式、术语定义、资源关系）全写明。小改大提升：原文说 Claude Sonnet 3.5 在 SWE-bench Verified 上达到 SOTA，靠的就是精修工具描述，大幅降低错误率、提升任务完成度。

口诀:「描述当 prompt 写，像带新员工；参数名一眼懂」
原文 "Prompt-engineering your tool descriptions"：user_id vs user、SWE-bench Verified 案例。

错误处理：错误也是 tool_result，不是异常

这条单独拎出来，因为它是原则 4 的延伸，也是 agent"自主性"在错误场景的落点：

工具失败时别中断 loop

工具执行出错（参数校验失败、资源找不到），不要抛异常中断整个 agent loop。把错误信息作为 tool_result（带 is_error: true）喂回模型，让它看到可操作的错误自己改路径——换参数、换工具、或告诉用户办不到。这才是 agent 的"自主"。

错误内容要 prompt-engineer：不说 "ERROR 500"，说 "customer_id 12345 not found, try search_customers(name='acme') first"。给 agent 一条可走的路，它就能自己走出来。

综合：坏工具 vs 好工具（客服场景）

把 5 原则串起来看一个完整对比：

维度坏设计好设计对应原则

本课小结

  • 心法：为 agent 设计，不是为开发者设计——agent context 金贵，把"找/拼"的活放回工具。
  • 原则 1 选对粒度：search 优于 list，整合多步，少而精。
  • 原则 2 namespacing：service + resource 前缀分组，防几百个工具打架。
  • 原则 3 返回有意义上下文：返名字不返 UUID，response_format 枚举兼顾 detailed/concise。
  • 原则 4 token 效率：CC 默认截断 25000，截断给指引，错误要可操作。
  • 原则 5 prompt-engineer 描述：像带新员工，参数名无歧义，小改大提升（SWE-bench 实证）。
  • 错误处理：错误作为 tool_result 喂回，不中断 loop，给 agent 一条可走的路。
小胜利

你现在拿到任何一个工具（自己写的、客户的、第三方的），能评判它好不好、知道往哪改——对着 5 原则逐条扫一遍：是 list 还是 search？返 UUID 还是名字？错误可操作吗？描述像给新员工吗？这就是售前/定制时的工具评审能力。

1客服工具 get_customer 返回 {"uuid":"4f3a...", "mime_type":"image/png", "256px_image_url":"..."}，模型拿到后还得再调一次工具才能用。这违反了哪条原则？识别

✓原则 1 选对工具粒度
✓原则 2 namespacing
✓原则 3 返回有意义上下文
✓原则 5 prompt-engineer 描述
答案：原则 3 返回有意义上下文。
  • 原则 1 ✗：原则 1 讲"选对工具/整合多步"（list vs search、schedule_event），本题考的是返回内容不对，不是工具选错。
  • 原则 2 ✗：namespacing 讲工具命名分组（asana_search/jira_search），与返回字段无关。
  • 原则 3 ✓：返回 uuid/mime_type/256px_image_url 这些 cryptic 标识符，agent 不能直接用，要再查。原文明确：应返 name/file_type/image_url 这类直接能用的字段。
  • 原则 5 ✗：原则 5 讲描述和参数名怎么写（user_id 而非 user），本题考返回值，不是描述。
口诀:「返名字不返 UUID」——agent 看得懂名字，看不懂 4f3a...。

2你给 agent 挂了 Asana 和 Jira 两个 MCP server，都要做"搜索"工具。工具名怎么取最不容易让 agent 混？应用

✓search——一个工具名，靠参数区分 service
✓asana_search / jira_search——按 service 前缀划开
✓asana_jira_search——一个工具塞两个 service
✓tool1_search / tool2_search——无意义编号
答案：asana_search / jira_search。
  • search ✗：两个 service 都叫 search 会重名，agent 不知道调谁的。无 namespace 就是 namespacing 原则要解决的痛点。
  • asana_search / jira_search ✓：按 service 前缀分组，边界清晰，agent 一眼选对。原文示例即此。可再按 resource 细分（asana_projects_search）。
  • asana_jira_search ✗：把两个 service 塞一个工具，违反"每个工具清晰独立用途"，参数也要复杂区分 service，反而更乱。
  • tool1/tool2 ✗：无意义名，agent 完全无法从名字判断用途，靠读描述猜，出错率飙升。
口诀:「名前缀划边界，service + resource 分组」——名字要能看出"谁家的、查什么"。

3工具执行时参数校验失败抛了异常。harness 怎么处理最符合 best practice？机制 · 排错

✓直接抛异常中断整个 agent loop，让开发者修 bug
✓把错误作为 tool_result（is_error:true）喂回模型，给可操作的改进建议
✓静默忽略错误，假装工具执行成功返回空结果
✓自动重试 3 次，还失败就崩溃退出
答案：把错误作为 tool_result 喂回，给可操作建议。
  • 抛异常中断 ✗：agent 的"自主"就体现在能从错误中改路径。中断 loop 等于剥夺 agent 自愈机会，用户每次小错都要开发者介入。
  • tool_result 喂回 ✓：错误也是 tool_result（is_error:true），让模型看到"customer_id 12345 not found, try search_customers first"这种可操作的错误，自己换路走。这正是 agent 区别于普通函数调用的关键。
  • 静默忽略 ✗：模型以为成功，基于空结果继续推理，必产出错误回答甚至幻觉。错误必须让模型看见。
  • 重试 3 次崩溃 ✗：参数校验失败是确定性错误，重试也是同样结果。盲目重试只对网络抖动这类瞬态错误有意义，且崩溃退出是最差处理。
口诀:「错误当结果喂回去，给可操作的提示」——别抛、别藏、给路。

4两段 get_weather 的 description，哪个更符合 best practice？
A："获取天气"
B："获取指定城市的当前天气。用于用户问天气/是否带伞/穿什么时调用。location 传城市名如 'NYC'，不支持经纬度。返回温度和天气状况。"应用

✓A——更短，省 token，description 不该写太长
✓B——写清何时用、参数格式、限制和返回，像给新员工解释
✓两个一样好，description 只是文档，agent 靠名字选工具
✓A 更好，因为模型训练时见过 get_weather，不需要描述
答案：B。
  • A ✗：太短，没说何时用、参数格式、限制。description 被拼进 system prompt 是 prompt 工程的一部分，省这几个 token 换来的是 agent 误用、参数猜错，得不偿失。
  • B ✓：像给新员工解释——写了何时用（问天气/带伞/穿衣）、参数格式（城市名如 NYC）、限制（不支持经纬度）、返回（温度+状况）。把隐含上下文全写明，正是原则 5 的要求。
  • "两个一样好" ✗：description 不是普通文档，它进 system prompt 直接引导工具调用行为（L06 已点）。原文说"even small refinements to tool descriptions can yield dramatic improvements"——Sonnet 3.5 靠精修描述拿下 SWE-bench SOTA。
  • "训练见过不需要" ✗：模型可能见过 get_weather 这个名字，但你的工具的参数格式、限制、返回结构是项目特定的，模型训练时没见过，必须靠 description 告诉它。
口诀:「描述当 prompt 写，像带新员工」——何时用、怎么传、返什么、有什么限制，全写明。
