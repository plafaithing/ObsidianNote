1同事说"CLAUDE.md 是系统提示词"，你说"它也是记忆"。CLAUDE.md 到底属于 harness 哪层？L01+L04 · 跨概念

✓只属于系统提示词层
✓只属于上下文与记忆层
✓跨两层：以文件形式存（记忆层），启动时拼进 system prompt（系统提示词层）
✓不属于任何层，是普通配置文件
答案：跨两层。
  • 只系统提示词 ✗：忽略了它本质是个 md 文件，存在 vault 里、跨会话持久——这是记忆层属性。
  • 只记忆层 ✗：忽略了 CC 启动时把它的内容拼进 system prompt 注入——这是系统提示词层行为。L01 quiz 选"上下文与记忆层"是存储视角，没毛病，但不全。
  • 跨两层 ✓：存储视角=记忆层，运行视角=系统提示词层注入。两个视角都对。
  • 普通配置 ✗：它塑造 agent 行为，不是死配置。
口诀:「CLAUDE.md 两幅面孔：存是记忆，注入是提示词」——很多 harness 部件跨层，别非此即彼。

2手写 Client SDK agent 的 while 循环里，run_tool(tool_call) 执行后，下一步 messages.create 要把什么喂回给模型？L02 · 机制

✓工具的描述文本（tool definition）
✓工具执行的结果（tool_result）
✓一句"工具已执行成功"
✓重新生成的 system prompt
答案：工具执行的结果（tool_result）。
  • 工具描述 ✗：tool definition 是调用前就给模型的（在 tools 参数里），不是喂回的东西。
  • tool_result ✓：以 user 角色的 tool_result 块喂回，和 assistant 的 tool_use 块配对，模型据此决定下一步。
  • "已执行成功" ✗：太模糊，模型需要真实结果内容才能继续推理。
  • 重新生成 system prompt ✗：system prompt 每次调用都带，但不是"喂回"的对象，且 API 无状态、要带全历史。
口诀:「喂回结果不喂描述，tool_use 配 tool_result」——见 Q&A Q2。

3售前客户要"完全自主、模型自己决定调什么工具、何时停"的 agent。实现路线选？L02 · SDK 选型

✓Agent SDK 的 query()——它封装了 while 循环，模型自主
✓Client SDK 手写 while 循环——代码控制每步
✓单次 messages.create 调用，不循环
✓用 workflow 固定步骤链
答案：Agent SDK 的 query()。
  • Agent SDK query() ✓：query() 把 while/工具调度/历史都封装了，Claude 自主决定调什么、何时停——正是"完全自主"。
  • Client SDK 手写 ✗：Client SDK 要你自己写 while 和 run_tool、自己管历史，是"你控制每步"的路线，不是"模型自主"。方向反了。
  • 单次调用 ✗：无循环=用完一个工具就停，无法多步自主。
  • workflow ✗：workflow 是预定义路径，模型不自主——和需求矛盾。
口诀:「模型自主 Agent，代码控步 Client」——见 Q&A Q4。

4客户要"读代码定位 bug、改多文件、跑测试"的系统，步数不可预测、要边走边探索。优先考虑？L03 · 售前判断

✓workflow（routing 路由模式）
✓agent（自主循环）
✓单次 LLM 调用加好检索
✓prompt chaining（提示链）
答案：agent。
  • routing ✗：routing 是分类后转固定流程，走向可预测。改 bug 步数不可预测，不是分类问题。
  • agent ✓：步数不可预测、要模型边走边探索→agent。Claude Code 干的就是这个。
  • 单次调用 ✗：Anthropic 忠告——能单次解决就单次，但多文件改 bug 显然超单次能力。
  • prompt chaining ✗：提示链是固定步骤串行，步数写死，不适合探索性任务。
口诀:「步数写死 workflow，写不死才 agent」——售前三问第一问。

5想让 Claude Code 默认"直接改代码"而非只给建议。system prompt 怎么写？L04 · 写法

✓"CRITICAL: You MUST implement changes immediately"
✓"不要只给建议"
✓"默认实施改动而非建议"
✓什么都不写，模型自己会懂
答案："默认实施改动而非建议"。
  • CRITICAL MUST ✗：新模型对激进语言过敏，会过度触发——本该问的时候也莽撞改。正常语气即可。
  • "不要只给建议" ✗：负面禁止，模型不知道该做什么。换成正面指令。
  • 正面写 ✓：说"做什么"（实施改动）而非"不做什么"，正常语气。即 Anthropic 文档 <default_to_action> 的思路。
  • 不写 ✗：默认行为是给建议，不写就不会动手。
口诀:「正面写做什么，别 CRITICAL MUST」——L04 两条原则叠加。

6你在 system prompt 加一句"删除文件、force push、影响共享系统的操作，先问用户"。这是用系统提示词调 harness 的哪层？L04+L05 · 控制面板

✓工具层（怎么调工具）
✓编排层（多 agent 派发）
✓权限/安全层（危险操作确认）
✓上下文层（窗口压缩）
答案：权限/安全层。
  • 工具层 ✗：工具层是"何时用哪个工具"，对应 CC 的 Tool use concepts 片段。
  • 编排层 ✗：编排层是多 agent 协调，对应 Coordinator mode orchestration 片段。
  • 权限/安全层 ✓：危险操作确认是安全行为，对应 CC 的 Executing actions with care 片段（1105 tks）。这就是"系统提示词=控制面板"——一句话调安全层。
  • 上下文层 ✗：上下文层是窗口/压缩，对应 Context compaction summary 片段。
口诀:「看行为认层」——确认危险=安全层，调度工具=工具层，派子任务=编排层。

7打开 Claude Code 真实 system prompt（Piebald 仓库，v2.1.220），它的结构是？L05 · 结构

✓一段写在配置文件里的长文本
✓515 段条件注入的片段，按环境/配置动态拼成
✓只有 CLAUDE.md 这一段
✓模型运行时自己生成
答案：515 段条件注入。
  • 一段长文本 ✗：这正是反直觉点——CC prompt 不是单段，是碎片化条件注入。
  • 515 段条件注入 ✓：分四类（主 prompt / 27 工具描述 / 子 agent / 工具型），按语言/模式/能力动态拼。
  • 只有 CLAUDE.md ✗：CLAUDE.md 只是用户层注入的一段。
  • 模型自己生成 ✗：system prompt 是 harness 侧注入，不是模型生成。
口诀:「五百段条件装，不是一段」——条件注入省 context 预算。

8售前客户想给 CC 加一条"改代码前先读文件"的行为。投入产出比最高的第一步？L05 · 定制入口

✓用 tweakcc 改 CC 内部 fragment
✓写进 CLAUDE.md，启动时自动注入
✓自建一套 harness 从头实现
✓改 Claude Code 源码重新编译
答案：写进 CLAUDE.md。
  • tweakcc ✗：能做但不是第一步。改内部 fragment，CC 升级可能冲突，需 diff 管理。
  • CLAUDE.md ✓：一句话注入即改行为，零维护、跨版本存活。CLAUDE.md 表达不了的深度定制才上 tweakcc。
  • 自建 harness ✗：过度方案，一句话能解决的事不值得自建。
  • 改源码 ✗：最重方案，CC 闭源升级即丢。
口诀:「定制先 CLAUDE.md，不够再 tweakcc，最后才自建」——从轻到重。
