RAG 是什么 & 为什么需要它

从「闭卷背诵」到「开卷考试」——理解 RAG 要解决的根本问题

← 上一节（已是第一节） 下一节：RAG 全流程地图 →

开场：一个会「一本正经胡说」的助手

假设你的 DBA Copilot 直接接上大模型就上线了。一位运维问它：「GaussDB 里慢 SQL 怎么定位？」模型自信地回答：「执行 SELECT * FROM slow_query_log 即可查看所有慢 SQL。」

问题在于——GaussDB 里压根没有这张系统视图，真实入口是 PGXC_STAT_ACTIVITY 和管控面的 Top SQL。模型编造了一个看起来很合理但完全错误的答案。这就是幻觉（Hallucination）。

运维场景的代价

在客服场景里，幻觉顶多让用户困惑；在运维场景里，幻觉 = 给错 SQL 建议 = 可能引发生产事故。这就是你的 DBA Copilot 必须用 RAG 的根本原因：不能让模型凭记忆瞎编，必须让它「看着文档说话」。

LLM 的三个固有限制

RAG 不是噱头，它针对的是大语言模型（LLM）三个绕不开的缺陷[1]：

  • 知识截止（Knowledge Cutoff）：模型训练有截止日期。你的私有运维文档、最新版本手册，模型训练时根本没见过。
  • 幻觉问题（Hallucination）：面对未知，模型倾向于「编」一个看似合理的答案，而不是老实说「不知道」。
  • 知识隔离（Knowledge Isolation）：模型无法访问企业私有数据、实时数据、个人文档——这些恰恰是售前客户最在意的东西。

注意这三个限制的本质：模型把知识「焊」在了参数里，参数一训练完就凝固了。而企业知识是活的——文档每周更新、版本每月迭代、客户数据每秒在变。用凝固的参数装活的知识，必然错位。

RAG 的核心思想：开卷考试

RAG（Retrieval-Augmented Generation，检索增强生成）的解法很直觉：别让模型闭卷背诵，让它开卷考试。

具体说，就是在大模型生成回答之前，先从外部知识库检索出与问题相关的文档片段，把这些片段塞进模型的上下文，让它基于检索到的内容生成答案（这就是「增强」）。

一句话定义

RAG = 检索（Retrieve）外部知识 + 增强（Augment）模型上下文 + 生成（Generate）回答。把「知识」从模型参数里搬到可随时更新的外部知识库里。

这个思路最早由 Lewis 等人在 2020 年提出，2023 年随 ChatGPT 爆发而产业化，2024 年进阶到 Self-RAG / CRAG，2025 年成为 Agentic RAG（和 Agent 结合）[1]。你现在学的是当下最主流的范式。

一图看全流程

RAG 分两个阶段：索引阶段（提前把知识准备好）和查询阶段（用户提问时实时检索+生成）。

索引阶段（离线，一次性 + 增量） 文档加载→ 切分 Chunking→ 向量化 Embedding→ 存入向量库 查询阶段（在线，每次提问） 用户问题→ 向量化→ 向量检索→ 重排 Rerank→ 组装上下文→ LLM 生成

不用现在就记住每个环节的细节——这正是第 02 节要深挖的。这里你只需要建立全景认知：RAG 不是一个「调一下」的开关，而是一条由 7+ 个环节组成的流水线，每个环节都有取舍。这条流水线的质量上限由最弱的环节决定。

RAG vs 微调 vs 长上下文

这是面试最高频的问题之一：「RAG、微调、长上下文，什么时候用哪个？」[2]

维度RAG微调 Fine-tuning长上下文 Long Context
知识更新即时生效，更新知识库即可需重新训练即时（塞进 prompt）
幻觉控制强（基于检索结果生成）弱（依赖模型记忆）中（取决于是否能找到）
成本低（无需 GPU 训练）高（训练资源）按 token 计费，长输入贵
数据安全可控（知识在本地索引）知识进参数，难删除数据进 prompt，注意泄露
适合场景知识频繁更新、需引用溯源改风格/格式/领域语感单次分析大量文档
长上下文 ≠ RAG 过时

现在模型上下文窗口动辄 200K，但 RAG 依然必要，三个原因[1]：

  1. 成本：长输入的推理费用与 token 数成正比，每次提问都塞几万字不划算。
  2. 迷失在中间（Lost in the Middle）：研究表明 LLM 对长上下文中间位置的信息召回率远低于首尾——塞进去不代表看得到。
  3. 延迟：超长上下文的首 token 延迟显著增加。

当前共识：长上下文与 RAG 是互补关系——RAG 负责精确定位相关文档，长上下文负责承载检索结果。

面试视角

Q：企业知识库每周更新，选 RAG 还是微调？为什么？

答 RAG。核心是知识更新即时生效：更新向量库索引后下次查询立刻生效；微调要把知识焊进参数，每次更新都重训，成本和时效都不可接受。再补一句「长上下文虽快但成本高且 Lost in the Middle」，就比只答 RAG 的候选人多了深度。

你的北极星：运维知识库 RAG

把这门课学到的东西，最终会汇聚成你的 DBA Copilot 的 RAG 部分：

  • 知识源：GaussDB 运维文档、慢 SQL 诊断手册、会话分析指南、SQL 限流规则、历史故障复盘。
  • 用户提问：「这条慢 SQL 为什么慢？」「怎么定位锁等待？」
  • RAG 做的事：检索出相关的运维文档片段 → 喂给大模型 → 模型基于文档生成带引用的诊断建议。

后续每节课，你都会为这个 demo 加一块拼图：切分运维文档、选 embedding、混合检索、rerank、防幻觉引用、评估效果。第 10 节用 Dify 端到端跑通。

小测验

企业内部文档每周都在更新，选 RAG 而非微调，最关键的原因是？

✓ 更新知识即时生效。 RAG 的知识在向量库里，更新文档即更新索引，下次查询立刻生效；微调要把新知识焊进模型参数，每次更新都要重训，频繁更新场景下成本和时效都不可接受。

推理延迟反而会因为多了检索环节而增加（所以「推理延迟能够降低」错）；RAG 不改变模型参数大小（所以「模型参数可以缩小」错）。这两个干扰项都是面试里真实会出现的误区。

✓ 本节胜利

你现在能用自己的话说清三件事：

  1. RAG 解决的根本问题是什么（LLM 知识凝固 vs 企业知识活的）。
  2. RAG = 检索 + 增强 + 生成，给模型「开卷考试」。
  3. 面对「RAG vs 微调 vs 长上下文」，你能给出带取舍的回答，而不是只说一句「RAG 好」。

这三点足够你在售前沟通和面试里把「为什么要 RAG」讲得比大多数候选人清楚。
