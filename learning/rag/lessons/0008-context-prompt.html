动机：检索满分，生成翻车

L05–L07 把检索侧三件套（embedding → 混合 → rerank）打磨好，Top-5 精排到位。但这 5 个 chunk 怎么拼成上下文喂给 LLM、用什么 prompt 约束它，决定了检索成果能不能转化成好答案。喂不好——LLM 无视上下文乱编（幻觉）、漏看中间的 chunk（Lost in the Middle）、输出格式没法接下游系统——前面白干。

本节定位

生成侧第一节。两件事：①上下文组装（Context Assembly）——把 Top-K chunk 拼好；②Prompt 工程——约束 LLM 用好上下文、不乱编。下一节 L09 讲怎么评估生成质量。

一、上下文组装（Context Assembly）

rerank 输出的 Top-K2（如 5 个 chunk）不能直接一锅炖喂 LLM，要处理四件事：

1. 顺序：Lost in the Middle

研究表明，LLM 对长上下文中间位置的信息利用差——呈 U 型曲线，头尾记得清、中间易忽略（Liu et al. 2023, Lost in the Middle）。

  • 简单做法（POC 够用）：按 rerank 分数降序拼，最相关的放最前面。首位效应最强。
  • 精细做法：最相关的放开头，次相关的放结尾，把可能被忽略的中间位置留给分数低的。
DBA 类比

像写 SQL 给领导看——最重要的结论放开头和结尾，中间塞细节。LLM 的"注意力"也一样，中间容易走神。

2. 去重与截断

  • 去重：同一段内容可能被多个 chunk 召回（尤其 overlap 切分时），重复喂浪费 token 还可能让 LLM 过度加权。按内容哈希或语义去重。
  • 截断：context 超 LLM 窗口时，按相关性分数从低到高砍，保留头部。别从中间砍（破坏 chunk 完整性）。

3. 元数据附带 + 引用编号

每个 chunk 拼进 context 时带上来源元数据（文档名/产品/版本/章节），并编上号 [1][2]...。两好处：①LLM 可以在答案里标注引用 [1]，可追溯防幻觉；②用户能点引用跳转原文（运维场景关键，DBA 要看原手册确认）。

[1] 来源：GaussDB v8.0 故障处理手册 · 慢SQL章节
    {chunk1 内容}

[2] 来源：GaussDB v8.0 参数调优指南 · 第3章
    {chunk2 内容}

4. Token 预算

LLM 窗口有限（8k / 16k / 32k / 128k 不等），要算账：

窗口 = system prompt + few-shot 示例 + context(Top-K) + 用户问题 + 生成预留

运维 RAG 的 chunk 一般不大（500-1500 token），Top-5 约 2-5k token，多数窗口够用。但加 few-shot 和长 chunk 时要算清，别把生成空间挤没。

二、Prompt 工程

1. 系统提示：角色 + 任务 + 防幻觉约束

系统提示（system prompt）定调子，三要素：角色、任务约束、防幻觉指令。

你是 GaussDB 资深 DBA，负责基于知识库回答故障诊断问题。

【规则】
1. 只依据下面提供的上下文回答，不要编造未在上下文中出现的内容。
2. 若上下文不足以回答，直接说"根据现有知识库无法诊断，建议联系..."，不要猜。
3. 答案中引用的信息要标注来源编号，如 [1]。
4. 处理步骤要具体可执行，不要泛泛而谈。

2. 结构化输出：JSON 约束格式

让 LLM 按固定 JSON 结构输出，方便下游系统（工单、UI）解析，也减少自由发挥导致的幻觉。运维故障诊断天然适合结构化：

请按以下 JSON 格式输出（不要输出其他内容）：
{
  "诊断": "一句话说明问题",
  "原因": "根因分析",
  "处理步骤": ["1. ...", "2. ...", "3. ..."],
  "风险提示": "操作风险或前置条件",
  "引用": [1, 2]
}
售前亮点

结构化输出是 RAG 对接企业系统的关键——答案能直接进工单系统的字段、能渲染成 UI 卡片。售前讲"RAG 不是聊天机器人，是能对接业务系统的知识引擎"，靠的就是这步。

3. 引用机制

要求 LLM 在答案里标注 [1][2] 引用编号，对应 context 里的 chunk 序号。好处：①可追溯（用户点 [1] 看原文）；②防幻觉（LLM 要引用就得真有依据）；③便于评估（L09 的 faithfulness 指标）。

4. Few-shot vs CoT：何时用

技巧是什么何时用运维 RAG
Zero-shot只给指令 + 上下文，不给示例任务简单、格式不复杂多数场景够用（系统提示 + 结构化输出）
Few-shot给 1-3 个输入-输出示例要引导固定格式/风格/边界行为需要统一诊断格式时，给 1-2 个标准示例
CoT（Chain of Thought）让模型分步推理（"逐步分析"）复杂推理（数学、根因链路）复杂故障根因分析可用；简单问答不要用——多花 token 和延迟
别滥用 CoT

运维 RAG 多数是"检索到 → 直接答"，零样本 + 结构化输出就够。CoT 用于需要多步推理的复杂诊断（如"现象 A + 现象 B → 推导根因"），简单事实问答用 CoT 只会增加延迟和 token 成本，还可能让模型绕弯子。

三、防幻觉四件套

RAG 本身是防幻觉的基础（给 LLM 依据），但 LLM 仍可能：①无视上下文编 ②过度推断 ③混淆多文档。四层防御：

层手段作用
①指令约束"只依据上下文""不知道就说不知道"明确边界，禁止编造
②引用要求答案标注 [1][2] 来源强制有据可循，可追溯
③低温度temperature=0~0.3降随机性，减少"创造"
④结构化输出JSON 固定格式 + 兜底字段约束表达空间，减少自由发挥
防幻觉不是靠单一手段

四层叠加才稳。只给指令"别乱编"不够——LLM 照编；只降温度不够——低温也会一本正经胡说。指令 + 引用 + 低温 + 结构化，组合拳。评估防幻觉效果靠 faithfulness 指标（生成内容是否忠于上下文），L09 讲。

四、运维实战：DBA Copilot 完整 prompt

把上面组装起来，一个运维 RAG 的完整 prompt 长这样：

【系统提示】

规则：①只依据上下文 ②不足就说"无法诊断，建议联系..." ③标注引用[1] ④步骤具体可执行。

【上下文】
[1] 来源：GaussDB v8.0 故障处理手册 · 慢SQL章节
    {rerank Top-1 chunk}

【用户问题】

【输出要求】

这个 prompt 涵盖了本节所有要点：角色约束、防幻觉指令、上下文带引用编号、按分数降序、结构化 JSON 输出。售前做 demo 直接能用。

面试视角 · 高频问题

Q：Lost in the Middle 是什么？怎么应对？
LLM 对长上下文中间信息利用差（U 型曲线）。应对：相关内容放开头（或头尾），按 rerank 分数降序拼；或压缩上下文别太长。

Q：RAG 怎么防幻觉？
四件套：指令约束（只依据上下文）+ 引用要求 + 低温度 + 结构化输出。RAG 本身给依据是基础，这四层是加固。

Q：few-shot 和 CoT 什么时候用？
few-shot 用于引导固定格式/风格；CoT 用于复杂多步推理。简单 RAG 问答零样本就够，别滥用 CoT（增延迟和成本）。

Q：上下文超 LLM 窗口怎么办？
按相关性分数从低到高砍，保留头部；或回到上游缩小 K2；或换更大窗口模型。别从中间砍破坏 chunk。

Q：为什么 RAG 答案要带引用？
可追溯（用户看原文）、防幻觉（强制有据）、便于评估（faithfulness）、企业场景合规要求。

小测验

Q1

rerank 输出 Top-5 chunk，要拼成 context 喂 LLM。关于拼接顺序，以下最合理的是？

✓ 降序拼，最相关在前。 Lost in the Middle 研究表明 LLM 对中间位置信息利用差（U 型曲线），头尾记得清。最相关的放开头（首位效应最强），简单做法就按 rerank 分数降序；精细做法把次相关放结尾。
为什么不能随机：LLM 注意力不均，随机拼可能让最相关的掉到中间被忽略。为什么不能放中间：中间最易被忽略，反着来。为什么按页码：原文顺序 ≠ 相关性顺序，检索排序白做了。

Q2

以下哪项不是 RAG 防幻觉的有效手段？

✓ 调大 K2 喂更多 chunk 不是防幻觉手段。 喂太多 chunk 反而加重 Lost in the Middle、挤占生成空间、增加噪声，可能加剧幻觉。防幻觉四件套是：①指令约束 ②引用要求 ③低温度 ④结构化输出。调大 K2 是检索侧动作，且要看窗口预算，不是防幻觉手段。

Q3

运维 RAG，用户问"ORA-01555 怎么处理"，检索 Top-5 已拿到相关 chunk。要 LLM 输出标准格式答案。该用？

✓ Zero-shot + 结构化 JSON。 这是简单事实问答 + 固定格式需求，零样本（系统提示 + 上下文 + JSON 要求）就够，结构化输出方便下游解析。
为什么不用 CoT：CoT 用于复杂多步推理（如根因链路推导），简单"检索到→直接答"用 CoT 只增延迟和 token，还可能绕弯。
为什么不能自由回答：没约束易幻觉、格式不统一没法接下游。
为什么不能只给 few-shot 不给上下文：RAG 的核心就是给检索上下文，不给上下文等于退化成纯 LLM。

Q4

context 拼好后发现超了 LLM 窗口。以下处理最合理的是？

✓ 按分数从低到高砍，保留头部。 rerank 已按相关性排序，砍掉低分的 chunk 损失最小。保留头部高分 chunk。
为什么不能从中间截断 chunk：破坏 chunk 语义完整性（L03 讲过切分要保完整），截断的 chunk 半句话没意义。
为什么不能全喂：超窗口会报错或被强行截断（不可控）。
为什么不能每个 chunk 截一半：同样破坏完整性，且损失关键信息。
根本解：若常超窗口，回到上游缩小 K2，或换更大窗口模型。
