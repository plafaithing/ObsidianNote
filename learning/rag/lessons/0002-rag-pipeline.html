一句话先立住系统观

第一节我们看了那张 7 环节的流程图。今天要建立的最重要认知是：

系统观

RAG 本质上是数据、切分、索引、召回、重排、上下文、生成、评估共同组成的系统工程，不是单点调参[2]。它的质量上限由最弱的环节决定，而不是由最强的环节撑起来。

这句话是整门课的「宪法」。售前沟通时，能把 RAG 当系统工程来谈（而不是「接个大模型 + 向量库就完了」），你就比多数候选人专业一档。

两条流水线：建图书馆 vs 读者查书

RAG 分两条流水线，时间维度完全不同：

  • 索引流水线（离线）：提前把知识准备好。好比建图书馆、给每本书编目录卡。
  • 查询流水线（在线）：用户每次提问时实时跑。好比读者来查书，图书管理员按目录找出来递给他。
DBA 视角类比（你的迁移优势）

索引流水线 ≈ ETL + 建索引：原始文档 → 清洗/切分 → 向量化 → 写入向量库（就像数据落表 + 建 B-tree/Hash 索引）。

查询流水线 ≈ 解析 + 执行计划 + 返回结果：query 向量化 → ANN 检索（走索引）→ rerank（排序优化）→ 组装上下文 → LLM 生成。

关键差异：关系库索引精确匹配，向量库做近似最近邻（ANN）——「近似」二字是 RAG 很多问题的源头，第 05 节会讲。

木桶效应：故障是链式的

理解 RAG 最重要的一件事：故障表现的地方，往往不是根因所在。

教学示例：一个运维 RAG 的链式故障

某团队 DBA Copilot 上线后，用户反馈「答非所问、答案残缺」。他们依次试了：换更大的 LLM → 换更强的 Embedding → 加更长上下文——都没用。

最后定位到根因：切分时把每条运维手册的「现象 / 原因 / 处理步骤」切到了不同 chunk。用户问「慢 SQL 怎么处理」，检索只命中了「现象」片段，LLM 拿不到「处理步骤」，自然答不全。

根因在切分（②），但表面看像「模型不行」（⑧）。团队一开始优化 ⑧、③、⑦ 全是错位——因为这些不是瓶颈。

真实数据点

HugoGu 记录过一次企业文档检索：固定 512 token 切分导致表格被截断，召回率从 85% 掉到 32%。改用按段落分割 + 200 token overlap 后恢复到 78%[1]。切分一变，召回率天差地别——这就是「决定上限」的含义。

推论：RAG 出问题，分环节量化定位远比「上来就换模型」有效。这正是环节⑨评估存在的意义，也是下面方法论的核心。

售前 POC 视角：优化优先级

客户做 POC 时资源有限，先优化哪个？这是售前最能体现专业度的问题。优先级（性价比从高到低）：

  1. 先把切分（②）调对——花时间理解客户文档类型。这是上限，错了后面全白费。[1]
  2. 上混合检索（⑤）+ Rerank（⑥）——性价比最高的优化，实现简单、效果显著[1]。Rerank 实测能让 Top3 命中率从 68%→89%[5]。
  3. 建立评估指标（⑨）——没有量化就没有方向，POC 报告里也拿不出「效果提升了多少」。
  4. 最后才考虑换模型/换框架——多数情况下不是模型问题。
迭代路径（wiki 总结）

MVP（Naive RAG：Embedding + 向量检索 + LLM）→ 优化（Chunking + 混合检索 + Rerank）→ 完善（HyDE / CRAG）→ 生产（评估 + 监控 + 缓存）→ 进阶（Agentic RAG / GraphRAG）[1]。

POC 阶段做到「优化」这一档就够讲了，能给客户演示明显效果提升。

评估先行：先量化，再优化

环节⑨为什么单独列出且贯穿全程？因为没法度量的东西就没法优化[5]。RAG 评估分两层（L09 详讲）：

  • 检索质量：Recall@K（相关文档有没有被召回）、MRR（相关结果排第几）。
  • 生成质量：Faithfulness（回答是否忠于检索文档）、Answer Relevancy（是否回答了问题）。

排查 RAG 故障的标准动作：先看检索指标——召回率低，问题在 ②③④⑤；召回正常但答案有幻觉，问题在 ⑦⑧。一刀切开「是不是模型不行」是最常见的外行反应。

面试视角

Q：RAG 效果不好，怎么排查？

不要答「换大模型」。标准答法：分环节量化定位。先看检索召回率——低则问题在切分/embedding/检索；召回正常但答案有幻觉则问题在上下文组装或生成。补一句口诀：「检索质量优先于生成技巧——再好的 prompt 也救不了错误的上下文」[1]。这个回答能筛掉一半只会说「RAG 就是检索+生成」的候选人。

Q：流水线里哪个环节最重要？ 答：切分决定上限（最易被忽视），检索+rerank决定下限（最显眼但可调）。两者都要，但先保证切分别拖后腿。

运维场景代入：DBA Copilot 的九环节

环节DBA Copilot 里具体是什么
① 解析GaussDB 运维手册（PDF/Confluence/HTML）→ 纯文本 + 章节结构
② 切分按「慢SQL诊断」「会话分析」「SQL限流」等章节切，保留「现象/原因/处理」完整不割裂
③ 向量化每个 chunk 用中文 embedding 模型编码
④ 存储向量 + 原文 + 元数据（产品版本/文档类型/SQL类别）写入 Milvus 或 pgvector
⑤ 检索用户问「慢SQL怎么定位」→ 向量（语义匹配诊断方法）+ BM25（精确匹配视图名如 PGXC_STAT_ACTIVITY）混合
⑥ 重排把「慢SQL诊断」章节片段排到「会话分析」前面
⑦ 组装Top 片段 + 用户问题 + 「请引用文档章节」指令 → prompt
⑧ 生成「根据[运维手册 §慢SQL]，可通过 PGXC_STAT_ACTIVITY 定位活跃会话…」带引用
⑨ 评估构造 50 个常见运维问题 + 标准答案，跑 Recall@5 和 Faithfulness

小测验

A、B 两团队都换了更强的 Embedding 模型，A 的召回率提升明显，B 几乎没变。B 的瓶颈最可能在？

✓ 文档切分。 Embedding 只能在切分给定的片段边界内编码语义。切分若把语义截断（表格切一半、现象与处理步骤分到不同 chunk），再强的 embedding 也只编码了残缺信息，召回率自然上不去。

A 团队切分本来就合理，换好 embedding 是锦上添花；B 团队瓶颈在切分，换 embedding 是错位优化——这正是「木桶效应」：优化非瓶颈环节无效。

向量检索和重排模型都在切分之后工作，切分残缺的片段传到它们手里，再调也补不回丢失的语义。所以排查 B 的问题，先查切分，而不是换 embedding/检索/rerank。

✓ 本节胜利

你现在掌握了三件售前/面试能直接用的东西：

  1. 系统观：RAG 是 9 环节系统工程，质量由最弱环节决定，不是「接个模型+向量库」。
  2. 排查方法论：效果不好时分环节量化定位，先查检索召回，再查生成，而不是上来换模型。
  3. POC 优化优先级：切分 → 混合检索+rerank → 评估 → 最后才换模型。这套排序能在客户面前体现专业判断。
