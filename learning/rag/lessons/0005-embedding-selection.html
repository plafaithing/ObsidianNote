把文本变成向量——选对模型，检索才有意义

Embedding 是什么

Embedding 就是把文本映射成一串数字（高维向量）。语义相近的文本，向量在空间里也相近——这就是向量检索的基础（Q&A 0001 里说的「画地图」）。

"慢SQL诊断"  →  [0.12, -0.45, 0.88, ..., 0.03]   # 1024 维向量
"SQL性能排查" →  [0.11, -0.43, 0.85, ..., 0.05]   # 语义相近，向量也相近
"备份恢复"    →  [-0.67, 0.21, -0.12, ..., 0.91]  # 语义无关，向量相差大

检索时，把用户问题也变成向量，算它和库里所有 chunk 向量的相似度（通常用 cosine），取最相似的 Top-K。

和数据库索引的本质区别（你有 DB 背景，这步关键）

DB 索引是人定义的规则（B-tree / Hash），做精确匹配——你查 WHERE id=123，索引精确找到 123。
Embedding 是模型从数据里学出来的语义空间，做相似度匹配——你问「慢SQL」，它能找到「SQL性能排查」，即使没有共同关键词。
代价：embedding 是「近似」（会漏、会混），不像 DB 索引那么精确。所以才有 L04 元数据过滤补结构化属性、L06 混合检索补精确匹配、L07 rerank 补排序。

运维场景推荐

BGE-M3——本地部署（数据不出域）、中文强、1024 维平衡、支持 8192 tokens 长文档。最关键的是它的稀疏向量功能：一个模型就能同时出稠密向量（语义）+ 稀疏向量（关键词，类似 BM25），一站式做混合检索（L06 会讲）。运维文档标识符多，这个特性正合适。

维度 vs 成本权衡

维度越高，表达力越强，但存储和计算成本线性上涨：

维度表达力存储/百万向量*检索延迟适用
768够用~3 GB快POC / 小规模
1024好~4 GB中⭐ 推荐，平衡点
1536强~6 GB较慢高精度需求
3072最强~12 GB慢极高精度 / 英文

*存储 = 维度 × 4 字节（float32）× 向量数。100 万 × 1024 × 4B ≈ 4 GB。HNSW 索引还要额外 1.5-2 倍。

别盲目追高维度

3072 维不一定比 1024 维效果好多少（边际递减），但存储和检索成本翻 3 倍。中文运维场景 1024 维是甜点。评测驱动：搭测试集跑 Recall@5，1024 够用就别上 1536。

运维场景的特殊性

运维文档有个特点：大量无语义的标识符——视图名（PGXC_STAT_ACTIVITY）、错误码（ORA-01555）、参数名（shared_buffers）。

这些标识符对 embedding 是难题：它们是「无语义」的字符串，embedding 模型理解不了 ORA-01555 和「快照太旧」的关联（除非训练语料里见过）。结果就是纯向量检索对精确标识符弱——这正是 Q&A 0001 里讲的「精确匹配弱」症状。

这不是 embedding 的锅，是它的边界

embedding 擅长语义相似（慢SQL ↔ SQL性能），不擅长精确匹配（ORA-01555 这个具体错误码）。解法不是换更强 embedding，而是混合检索（L06）——用 BM25 补精确匹配。BGE-M3 的稀疏向量功能正好一站搞定。

C-MTEB 榜单怎么用

C-MTEB（Chinese Massive Text Embedding Benchmark）是中文嵌入模型最权威的综合榜单，覆盖分类、聚类、检索、相似度等任务[1]。

  • 看 Retrieval（检索）子榜——和 RAG 最相关，其他子榜（分类/聚类）参考意义小
  • 榜单是通用语料测的，你的运维语料可能不一样——别盲信，要自测
  • 自测方法：搭 50 题运维测试集，跑 Recall@5 对比几个候选模型
面试视角

Q：中文 RAG 选什么 embedding？ BGE-M3 或 GTE-Qwen2——中文优化、可本地部署、C-MTEB 检索子榜高分。OpenAI text-embedding-3 中文一般、贵、数据出境（运维场景敏感）。BGE-M3 还支持稀疏向量，一站式做混合检索。

Q：维度怎么选？ 1024 是平衡点。高维表达力强但存储/检索成本线性涨，边际递减。POC 用 768/1024 够，评测驱动，别盲目追高维度。

Q：换 embedding 要注意什么？ ①要重新向量化整个知识库（成本高，10 万文档要算时间）；②维度变了要重建向量索引；③所以 L02 说换模型放 POC 优化最后——先治切分/检索/评估这些廉价环节。

Q：embedding 和 BM25 什么关系？ embedding 是稠密向量（语义相似），BM25 是稀疏关键词（精确匹配）。运维场景标识符多，纯 embedding 弱，需混合（L06）。

小测验

场景

团队用 OpenAI text-embedding-3 搭运维 RAG，效果不好，召回率低。运维文档是中文，含大量错误码（ORA-01555）和视图名（PGXC_STAT_ACTIVITY）。以下改进最合理的是？

✓ 换 BGE-M3 + 加 BM25 混合检索。 两个问题分开治：
① 中文适配差→ 换 BGE-M3（中文优化、C-MTEB 高分、本地部署）。
② 标识符检索弱→ 加 BM25 混合检索（embedding 救不了 ORA-01555 这种精确标识符，BM25 补）。
BGE-M3 自带稀疏向量功能，一个模型就能做混合检索。

为什么不是「换 3072 维更强模型」：维度高不解决中文适配（OpenAI 中文仍一般），也不解决标识符精确匹配。成本翻 3 倍却没治根因——盲信维度是选型反模式。
为什么不是「在 OpenAI 上微调」：OpenAI 不支持私域微调 embedding 模型；即便能微调，POC 阶段成本太高，应先评测通用模型。
为什么不是「增大 K」：K 大只是多召回，不解决中文理解差和标识符弱的根因，还增噪声和 rerank 成本。

口诀：语言不适配换中文模型，精确匹配弱上混合检索——对症下药，别靠「更大」。

✓ 本节胜利

你现在掌握了：

  1. Embedding 本质——把文本变成向量做相似度匹配，和 DB 索引（精确匹配）是两套思路。
  2. 选型四维度——语言适配、维度、效率、效果，评测驱动。
  3. 中文推荐——BGE-M3（三合一、1024 维、本地部署）是运维场景首选。
  4. 维度权衡——1024 是平衡点，别盲目追高维（边际递减、成本翻倍）。
  5. embedding 的边界——擅长语义相似，不擅长精确标识符 → L06 混合检索的动机。
