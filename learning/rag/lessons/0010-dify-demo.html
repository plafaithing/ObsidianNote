动机：概念到 demo 的最后一公里

L01–L09 学完了 RAG 全链路概念：切分、embedding、混合检索、rerank、上下文组装、prompt、评估。但概念不会自己变成能演示的东西。这节用 Dify（低代码 LLM 应用平台）把它们端到端跑通成一个 DBA Copilot RAG demo——不用写代码，拖拽配置就能把上面所有概念对上号。

本节定位

M5 实战第一节。你已用过 Dify（NOTES 确认），所以不讲基础 UI，重点是把 L01–L09 每个概念对应到 Dify 哪个配置项，给一个可照做的最小 demo 流程 + 踩坑 + 售前边界。这是北极星 demo（运维知识库 RAG）的落地。

一、准备清单

  • Dify 环境：cloud.dify.ai 免费试（最快），或 Docker Compose 自部署（社区版，可控）
  • 生成用 LLM 的 API key：DeepSeek / 通义千问 / GPT-4o-mini 任一（DBA Copilot 生成答案用）
  • Embedding 模型：Dify 自带若干；中文运维语料推荐接入 BGE-M3（via Xinference / Ollama / SiliconFlow）
  • Rerank 模型 API：Cohere / Jina，或本地 bge-reranker-v2-m3（L07 推荐的运维首选）。注意：embedding 模型和 rerank 模型是两个独立模型，都要配（L07 易混点）
  • 运维文档：准备 4 个主题的手册片段（markdown/pdf）——慢SQL诊断、会话分析、SQL限流、参数调优，每个 3-5 页。这是知识库的料。
售前 tip

POC 阶段用 cloud.dify.ai 最快，半小时出 demo。要给客户私有化部署演示时再用 Docker 自部署。文档料不用多，4 个主题 × 3-5 页 = 12-20 页够 demo 了，重点是覆盖典型问题。

三、5 步搭 demo（可照做）

步骤 1：建知识库 + 上传文档

知识库 → 创建知识库 → 上传 4 个主题的运维文档（md/pdf）。Dify 会用 ETL 解析（SaaS 版默认 Unstructured ETL，社区版可选 Dify ETL）。

步骤 2：分段（L03 落地）

  • 分段模式：选「自定义」（运维文档有结构，自定义比自动好）
  • 分段最大长度：500-800 token（运维操作步骤要完整，别太碎）
  • 分段标识符：按 \n\n + 标题
  • overlap：50-100（避免操作步骤被截断）
  • 预览分段：确认没把一个操作步骤切成两段——这是 L03 强调的"切分要保语义完整"

步骤 3：索引 + 检索设置（L05/L06/L07 落地）

  • Embedding 模型：选中文好的（接入的 BGE-M3，或 Dify 自带中文模型）
  • 检索模式：选「混合检索」——运维场景既有语义问题（"数据库慢怎么排查"）又有精确问题（"pg_stat_statements 视图"），混合最合适（L06）
  • Rerank 模型：选 bge-reranker-v2-m3（中文+本地，L07 推荐）。混合检索强制要配 rerank，因为要融合两路结果
  • TopK：先设 5（rerank 后喂 LLM 的数量，对应 L07 的 K2）
  • Score 阈值：先关（POC 先看全召回，再调）
  • 等待分段嵌入完成
TopK 在 rerank 前后的含义（Dify 关键细节）

Dify 文档明确：设置了 Rerank 模型后，TopK 和 Score 阈值仅在 Rerank 步骤生效。即向量/全文两路各自召回一批（K1，Dify 内部定），rerank 后再按 TopK 取前 N（K2）喂 LLM。你配的 TopK 是 K2（最终喂 LLM 的数量），不是 K1。这正好对应 L07 的两阶段 K1→K2。

步骤 4：召回测试（L09 落地，肉眼体检）

  • 知识库 → 召回测试
  • 输入典型问题：「ORA-01555 怎么处理」「慢SQL怎么定位」「pg_stat_statements 怎么查」
  • 看召回的区块 + 右上角分数：相关文档排前面没？分数合理没？
  • 点区块可看引用详情和来源文档，判断分段合不合理
这就是 L09 说的"最朴素检索体检"

召回测试 = 肉眼看召回对不对，不用跑 RAGAS。POC 初筛够用：相关文档没召回 → 检索侧问题（embedding/切分）；召回了但排后面 → rerank 或 TopK 问题。对应 L09 的"评估驱动定位瓶颈"，只是用眼睛代替 RAGAS。

步骤 5：建应用 + 关联知识库 + prompt（L08 落地）

  1. 创建「聊天助手」应用
  2. 上下文 → 关联刚建的知识库
  3. 开「引用与归属」开关（L08 引用机制落地）——LLM 回答下方会显示引用段落（原始分段文本、分段序号、匹配度），点引用可跳转知识库
  4. 系统提示词（直接用 L08 的 DBA Copilot prompt）： 
    你是 GaussDB 资深 DBA，基于知识库回答故障诊断问题。
规则：①只依据上下文 ②不足就说"无法诊断，建议联系..." ③标注引用 ④步骤具体可执行。
  5. 模型温度：0.2（L08 防幻觉四件套之低温度）
  6. 保存 → 测试几个问题，看引用对不对、有没有幻觉
demo 跑通检查清单

✅ 问"ORA-01555 怎么处理"，答案引用了正确的故障手册段落
✅ 答案下方有引用归属（[1] 来源：xxx手册），点开能看到原文
✅ 问知识库没有的问题（如"Oracle 的 xxx"），AI 说"无法诊断"而不是编
✅ 召回测试里相关文档排在前面、分数合理
四条都过，demo 就能演示了。

四、踩坑提示

  • 混合检索不配 rerank 会出问题：Dify 混合检索强制要 rerank 模型（两路结果要融合）。没配 API key 会报错或效果差。
  • TopK 默认 3 太小：运维多步诊断常需多文档，3 个不够。调到 5-8。但别太大（Lost in the Middle，L08）。
  • 分段太碎：操作步骤被切断，召回半句话没意义——加大分段长度 / overlap，或换分段标识符。预览时就要发现。
  • embedding 和 rerank 是两个模型：都要配 API key，别只配一个（L07 易混点）。
  • 引用与归属要在应用里开：知识库建好 ≠ 应用能看到引用。要在应用编排的"添加功能"里开。
  • 中文文档别用英文 embedding：运维语料中文为主，用英文 embedding 召回会很差（L05）。BGE-M3 是安全选择。

五、从 demo 到 POC：评估闭环（L09 落地）

Dify 不内置 RAGAS，四指标自动评估要外接。POC 闭环这么搭：

  • 检索侧（Dify 内）：用召回测试做肉眼评估，调 embedding/切分/TopK/rerank——POC 初筛够用
  • 生成侧（外接）：把应用跑的问答记录导出，用 RAGAS 代码（Q&A 0013）评 faithfulness / response relevancy
  • 监测（Dify 集成）：Dify 支持接 Langfuse / LangSmith / Opik（文档目录里有），线上问答自动记录，可追溯每条的检索上下文和生成答案——这正是 Q&A 0012 说的"记录中间产物"
售前闭环

召回测试调检索 → 改 prompt 调生成 → 导出问答评 RAGAS → 定位瓶颈（L09 闭环）→ 回 Dify 调对应配置。Dify 搞定 demo 和检索调试，RAGAS/Langfuse 搞定评估和监测，分工清楚。

六、Dify 能做什么 / 不能做什么（售前边界）

具体
能低代码搭 RAG demo、混合检索+rerank、引用展示、召回测试、多轮对话、元数据基础过滤、接 Langfuse 监测
不能（要外接/迁框架）RAGAS 自动评估、复杂查询重写（多轮，L09 Q&A 0014）、元数据高级过滤、生产级定制逻辑、复杂工作流编排（要用 ChatFlow）
售前话术

Dify 是 POC 出 demo 的最快路径——半小时搭出能演示的 DBA Copilot RAG。但生产级定制（复杂查询重写、定制评估管线、深度监控）可能要迁 LangChain/LlamaIndex 写代码（你的路径 C：能读改 LangChain）。售前讲清这条边界，显得懂落地节奏：先 Dify 验证效果，再决定是否迁代码框架。

面试视角 · 高频问题

Q：Dify 的混合检索和 rerank 怎么配？
建知识库第 3 步检索设置里，检索模式选「混合检索」（向量+全文），它强制要配 Rerank 模型（两路结果要融合）。rerank 选 bge-reranker-v2-m3（中文运维）。设了 rerank 后，TopK 仅在 rerank 步骤生效（即 K2，最终喂 LLM 的数量）。

Q：Dify 里 TopK 在 rerank 前后分别什么意思？
不设 rerank 时，TopK 是向量/全文检索直接召回的数量（K1=K2）。设了 rerank 后，Dify 文档明确 TopK 和 Score 阈值仅在 rerank 步骤生效——即两路各自召回一批（K1，内部定），rerank 后按 TopK 取前 N（K2）喂 LLM。对应 L07 两阶段 K1→K2。

Q：怎么在 Dify 里做检索评估？
用知识库的「召回测试」：输入典型问题，看召回的区块和分数，相关文档排前面没、分数合理没。这是 L09 说的"最朴素检索体检"，肉眼代替 RAGAS，POC 初筛够用。四指标自动评估要外接 RAGAS（Dify 不内置）。

Q：Dify 搭 RAG demo 的局限？
RAGAS 自动评估、复杂查询重写（多轮）、生产级定制逻辑要外接或迁 LangChain/LlamaIndex。Dify 是 POC 出 demo 最快路径，生产定制可能要迁代码框架。售前要讲清这条边界。

Q：运维 RAG 在 Dify 里分段怎么配？
自定义分段（运维文档有结构），分段最大长度 500-800 token（操作步骤要完整），overlap 50-100（避免步骤截断），按 \n\n+标题分段。预览确认没把一个操作步骤切成两段——切分要保语义完整（L03）。

小测验

Q1

在 Dify 配混合检索时，为什么必须配 Rerank 模型？

✓ 混合检索要融合两路结果，必须 rerank。 向量和全文两路各自召回一批，结果要合并重新排序选最佳——这步就是 rerank 干的（L06 RRF / L07 rerank）。没 rerank 两路结果没法融合，Dify 强制要求配。
为什么不是"提升召回率"：rerank 提的是排序精度（precision），不增加召回（L07）。混合检索本身已通过两路互补提了召回。
为什么不是"推荐"：Dify 混合检索模式强制要 rerank 模型 API，不配会报错。

Q2

Dify 检索设置里 TopK 默认 3，运维 RAG 场景该怎么调？

✓ 调到 5-8。 运维多步诊断（如慢SQL+锁+参数）常需多个文档片段拼起来答，3 个不够。但别太大——Lost in the Middle（L08），喂太多 LLM 反而忽略中间的，还挤占生成空间。5-8 是运维甜点。
为什么不是保持 3：运维诊断常跨多个手册章节，3 个易漏关键文档。
为什么不是 30-50：Lost in the Middle + token 预算，喂太多反降质量（L08）。
注意：设了 rerank 后这个 TopK 是 K2（rerank 后喂 LLM 的数量）。

Q3

Dify 的「召回测试」功能能看到什么？对应 L09 评估流程的哪一步？

✓ 看召回的区块和分数，对应检索侧肉眼体检。 召回测试输入问题后，显示召回的文档区块（按分数排序）+ 右上角匹配分数 + 来源。这是 L09 说的"最朴素检索体检"——肉眼看召回对不对，不用跑 RAGAS，POC 初筛够用。
为什么不是 faithfulness：faithfulness 是生成侧指标（查 LLM 有没有编），召回测试只看检索不看生成。
为什么不是四指标：Dify 不内置 RAGAS，召回测试只给原始召回结果，不给四指标分数。四指标要外接 RAGAS。

Q4

想让 DBA Copilot 的回答带引用来源（用户能点开看原文），在 Dify 哪里开？对应 L08 的什么？

✓ 应用编排「添加功能」开「引用与归属」。 知识库建好 ≠ 应用能看到引用。要在应用编排的"上下文"关联知识库后，在"添加功能"里开「引用与归属」开关，LLM 回答下方才会显示引用段落（原始分段文本、序号、匹配度），点引用可跳转知识库。对应 L08 的引用机制（可追溯 + 防幻觉 + 评估用）。
为什么不是检索设置：引用展示是应用层功能，不是检索层配置。
为什么不能只靠 prompt：prompt 里写"请带引用"只能让 LLM 输出 [1] 文字，真正的"点引用跳原文"要靠引用与归属功能渲染——这是 L08 说的"引用机制落地"。
