RAG 评估：定位瓶颈，而不是凭感觉调参

检索准不准、生成忠不忠实——四个指标给 RAG 链路出体检报告

← 上一节：上下文组装与 Prompt 工程 下一节：Dify 搭运维知识库 RAG demo →

动机：不评估就是"凭感觉调参"

L01–L08 把 RAG 全链路走完：ingest → embed → store → retrieve → rerank → 上下文组装 → generate。但效果不好时——用户问"ORA-01555 怎么处理"，答案不对——错在哪一环？是切分太碎（L03）？embedding 选错（L05）？rerank 没排好（L07）？还是 prompt 没约束住（L08）？

不评估就只能瞎猜着调参：加大 K、换模型、改 prompt……改完也不知道是好是坏。评估的作用就是把"感觉"变成"数字"，定位瓶颈在哪一环，再回去精准调。

本节定位

M4 收口，也是整个质量体系的最后一节。两件事：①用四个核心指标量化检索和生成质量；②建立评估驱动优化闭环——评估 → 定位瓶颈 → 回对应环节调 → 再评估。售前 POC 时，客户问"你怎么证明你的 RAG 有效？"评估指标就是答案。

一、为什么评估难：链路长，错在哪不知道

RAG 不是单一模型，是一条链路。最终答案错，根因可能在任何一环。两种评估策略：

  • 端到端评估：直接看最终答案对不对。简单，但只知道差，不知道哪差——答案错可能是检索没召回，也可能是召回了但 LLM 没用好。
  • 分环节评估：检索环节单独评估（召回准不准）、生成环节单独评估（忠不忠实、答没答对）。能定位瓶颈，售前讲这个显专业。
售前关键

分环节评估 = L02 木桶效应的落地。RAG 效果上限由最短板决定，评估就是找最短板。客户最怕你"整体看着行，但不知道哪里会崩"——分环节指标让他看到你知道每个环节的水位。

二、四大核心指标：两大维度 × 两个方向

RAG 评估分两大维度：检索质量（L05-L07 的成绩单）和生成质量（L08 的成绩单）。每个维度两个核心指标，正好四个——这也是 RAGAS 框架的四个招牌指标。

检索侧：召回全不全 + 排序准不准

指标看什么怎么算低了说明
Context Recall
上下文召回		该召回的信息漏没漏把标准答案（reference）拆成一条条 claim，逐个判断能否被检索到的上下文支撑。能支撑的 / 总 claim 数检索召回不足，相关文档没找回来 → 上游（embedding/混合/切分）
Context Precision
上下文精确		相关 chunk 有没有排在前面各位置 precision@k 的均值，位置敏感。相关 chunk 在第 1 位比在第 5 位分数高排序差，相关 chunk 排在后面 → rerank / ef 调参

生成侧：有没有编 + 答没答对

指标看什么怎么算低了说明
Faithfulness
忠实度		答案有没有编造（幻觉）把 LLM 答案（response）拆成 claim，逐个判断能否被检索上下文支撑。能支撑的 / 总 claim 数LLM 在编，防幻觉没做好 → prompt 约束 / 低温 / 结构化（L08 四件套）
Response Relevancy
答案相关度		答案有没回答问题（不跑题、不啰嗦）LLM 反推：从答案反推出可能的问题，看和原问题多相关。啰嗦/跑题扣分答非所问或冗长 → prompt / 检索相关度
关键辨析：Context Recall vs Faithfulness

这俩结构对称，最容易混：

  • Context Recall：拆的是 reference（标准答案）的 claim → 问"检索上下文够不够支撑标准答案" → 查检索全不全。
  • Faithfulness：拆的是 response（LLM 生成的答案）的 claim → 问"LLM 答的有没有超出上下文" → 查生成有没有编。

一个查"该有的有没有"，一个查"有的有没有被乱加"。Faithfulness 就是 L08 防幻觉四件套的体检报告——四件套做得好不好，faithfulness 分数说了算。

Context Precision ≠ Recall 的"窄窗口"混淆

L07 讲 rerank 时提过"窄窗口 recall 其实是 precision"——那是在 K1→K2 窄窗口语境下的口语化说法。本节给准确定义：Context Recall 看"该召回的漏没漏"（不漏），Context Precision 看"召回的排没排前"（位置）。运维 RAG 里，Precision 低意味着相关 chunk 召回了但排在第 5 位，LLM 可能根本没看到（Lost in the Middle，L08）——所以 rerank 才重要。

三、RAGAS 框架：LLM 当裁判，省掉大规模标注

上面四个指标的"拆 claim、判断能否被支撑"靠谁做？RAGAS（Retrieval-Augmented Generation Assessment）这个开源框架的做法是：用 LLM 当裁判（LLM-as-a-Judge），自动完成拆 claim 和判断。

核心价值

  • 弱参考 / 无参考：传统评估要人工标注每条问题的"标准答案 + 相关文档"，成本极高。RAGAS 部分指标（如 Faithfulness、Response Relevancy）不需要标准答案，只要检索上下文 + LLM 答案就能打分；Context Recall 需要参考答案但也是 LLM 自动算。
  • POC 快速迭代：售前做 POC 时，造 50 条问题跑 RAGAS，几分钟出四指标分数，不用人工逐条评——这是 RAGAS 在 POC 阶段的最大价值。

输入与输出

# RAGAS 评估单条样本需要的输入
{
  "user_input":        "ORA-01555 怎么处理？",        # 用户问题
  "retrieved_contexts": [chunk1, chunk2, ...],        # 检索到的上下文（L05-L07 的输出）
  "response":          "ORA-01555 是快照过旧...",      # LLM 生成的答案（L08 的输出）
  "reference":         "ORA-01555 快照过旧，需..."     # 标准答案（部分指标需要，如 Context Recall）
}
# 输出：四个指标各一个 0~1 的分数
售前亮点

POC 客户最常问："你这 RAG 准确率多少？"——别只答"感觉不错"。用 RAGAS 跑评估集，给出"Context Recall 0.87、Faithfulness 0.94、Response Relevancy 0.91"这样的数字，再讲清楚每个指标对应哪个环节、瓶颈在哪、怎么优化。这是售前和"调 API 的"的分水岭。

四、补充：传统检索指标（Recall@K / MRR / NDCG）

RAGAS 的 Context 指标是 LLM-as-Judge 版。还有一类传统检索指标，需要人工标注的"相关文档 ID"（ground truth），不调 LLM，更准更便宜：

指标看什么怎么算DBA 类比
Recall@KTop-K 里召回了多少相关文档Top-K 中的相关文档数 / 全部相关文档数查询返回的行里，命中的目标行占所有目标行的比例
Precision@KTop-K 里多少是相关的Top-K 中的相关文档数 / K返回的行里有多少是想要的
MRR
Mean Reciprocal Rank		第一个相关文档的位置1/第一个相关文档的位置。第 1 位=1.0，第 5 位=0.2。多 query 取平均第一条命中的结果在第几行——越靠前越好
NDCG位置加权的相关性前面位置权重高，相关文档越靠前分越高；支持多档相关度加权排名评分，前排命中得分高
POC 怎么选

有标注（标注了相关文档 ID） → 用传统指标（Recall@K / MRR），不调 LLM、零成本、确定性。没标注 → 用 RAGAS 的 LLM-as-Judge 版（Context Precision/Recall），省标注但要花 LLM 调用钱、且有不稳定性。运维 POC 推荐：先人工标注 50 条的相关文档 ID，用传统指标评检索（准、便宜），生成侧用 RAGAS 的 Faithfulness/Response Relevancy（这俩本就需要 LLM 判断）。

五、评估集怎么造：运维场景实战

评估的前提是有评估集（Golden Set）。没有评估集，跑不出指标，调参就是瞎调。造评估集比调参重要——这是 POC 第一步。

运维 RAG 评估集设计

  • 规模：50-200 条典型问题。POC 阶段 50 条高质量够用，不必贪多。
  • 来源：真实工单（最金贵）、DBA 常见问题、历史故障案例、产品手册目录反推问题。
  • 每条标注：
    • 问题（user_input）
    • 相关文档/chunk ID（检索 ground truth，算 Recall@K/MRR 用）
    • 标准答案（reference，算 Context Recall/Faithfulness 用，可选）
  • 分层覆盖（别只出简单题）：
    • 简单事实型："GaussDB 默认端口是多少"
    • 多步诊断型："慢SQL + 锁等待同时出现怎么排查"（考多 chunk 召回）
    • 边界型（知识库没有的）："Oracle 的 XXX 怎么配"（考"该说不知道"，防幻觉）
    • 易混淆型："undo 和 redo 的区别"（考精确排序，rerank 价值在这）
DBA 类比

评估集 = 数据库的回归测试集。改索引/调参数前先跑一遍，看是变好还是变坏。RAG 也一样——换 embedding、调 rerank K1、改 prompt 前，先跑评估集，用数字说话，别凭感觉。

六、LLM-as-a-Judge 的坑

RAGAS 用 LLM 当裁判，但 LLM 裁判不是金标准，有已知偏差：

  • 偏好长答案（verbosity bias）：答案越长越容易得高分，哪怕啰嗦。
  • 偏好自己风格（self-enhancement）：用 GPT-4 评 GPT-4 的答案会偏高。
  • 位置偏见：信息在上下文里的位置影响判断（呼应 L08 Lost in the Middle）。
  • 不稳定：同样的输入跑两次，分数可能不同（温度不为 0 时尤其）。
售前要诚实

别跟客户吹"LLM 评估全自动、百分百准"。正确说法：LLM 评估用于大规模快速扫描，人工抽检校准。具体做法：①评估裁判用更强模型（如 GPT-4 评 GPT-3.5 的生成）；②固定 seed / temperature=0 降不稳定；③人工标注一小撮校准集（50-100 条），和 LLM 分数对比算相关性，校准 LLM 裁判。客户问起局限性，你能主动讲，反而加分。

七、评估驱动优化闭环

评估的目的不是打分，是定位瓶颈 → 回对应环节调。这是 L02 木桶效应 + POC 优化优先级的落地：

指标低瓶颈环节回去调什么
Context Recall 低检索召回embedding 选型 / 加混合检索（L06）/ 加大 rerank K1 / 切分太碎回 L03
Context Precision 低检索排序上 rerank 或调 rerank（L07）/ 调 HNSW ef（参考速查表）
Faithfulness 低生成幻觉L08 防幻觉四件套：指令约束 + 引用 + 低温 + 结构化输出
Response Relevancy 低生成相关度prompt 改（明确任务）/ 检索相关度（Context Precision 是不是也低）
闭环

评估 → 定位瓶颈 → 回对应环节调 → 再评估（确认指标涨了）→ 看下一个瓶颈。每次改只改一个变量，跑评估集对比，才知道改动有效没。和 DBA 调优一个思路——改一个参数跑一次基准，别一次改一堆。

八、运维实战：DBA Copilot 评估设计

把上面组装起来，DBA Copilot RAG 部分的评估方案：

  1. 造评估集：50 个 GaussDB 运维问题（慢SQL诊断 / 会话分析 / SQL 限流 / 参数调优），标注相关手册章节 ID + 部分标准答案。分简单/多步/边界/易混淆四类。
  2. 跑一版基线：用当前配置（如 BGE-M3 + HNSW + 混合 + rerank K1=50/K2=5）跑 50 条，出四指标分数。
  3. 定位瓶颈：假设 Context Recall 0.72（低）、Faithfulness 0.95（高）→ 瓶颈在检索召回，不是生成。
  4. 回对应环节调：Context Recall 低 → 查切分（太碎？）、查 embedding（运维语料表现？）、加大 K1、补 BM25 混合。每次改一个，跑评估集对比。
  5. 迭代到达标：定目标（如 Context Recall ≥ 0.90、Faithfulness ≥ 0.95），迭代到达标。
  6. 交付评估报告：四指标分数 + 瓶颈定位 + 优化路径 + 评估集说明。这是售前 POC 的核心交付物。
售前交付物

POC 结束别只交个 demo。交评估报告：评估集怎么造的、四指标多少分、瓶颈在哪、已优化到什么水平、下一步优化方向。客户看到这个，知道你不只是"调了个 API"，而是有方法论的解决方案。这是售前溢价的核心。

面试视角 · 高频问题

Q：RAG 怎么评估？四个核心指标是什么？
检索侧：Context Recall（该召回的漏没漏）、Context Precision（相关 chunk 排没排前）。生成侧：Faithfulness（答案有没有编）、Response Relevancy（答没答对问题）。RAGAS 框架把这四个封装好，用 LLM-as-Judge 自动算。

Q：Faithfulness 和 Context Recall 区别？
结构对称但查的东西不同。Context Recall 拆 reference（标准答案）的 claim，看检索上下文够不够支撑标准答案 → 查检索全不全。Faithfulness 拆 response（LLM 答案）的 claim，看 LLM 有没有超出上下文编造 → 查生成幻觉。一个查"该有的有没有"，一个查"有的有没有被乱加"。

Q：为什么要分环节评估，不直接看最终答案？
RAG 是链路，最终答案错根因可能在检索也可能在生成。端到端评估只知道差不知道哪差，分环节评估能定位瓶颈——检索召回不足回 embedding/混合/切分，生成幻觉回 prompt/防幻觉。这是精准优化 vs 瞎调参的区别。

Q：RAG 评估集怎么造？
50-200 条典型问题，来源真实工单/常见问题/历史案例。每条标注问题 + 相关文档 ID（检索 ground truth）+ 标准答案（生成 ground truth，可选）。要分层覆盖：简单事实 / 多步诊断 / 边界（知识库没有的）/ 易混淆。造评估集比调参重要——没评估集，调参是瞎调。

Q：LLM-as-a-Judge 有什么局限？
偏好长答案、偏好自己风格、位置偏见、不稳定。缓解：用更强模型评、固定 seed/低温、人工标注校准集校准 LLM 裁判。售前要诚实——LLM 评估用于大规模快速扫描，人工抽检兜底，不是金标准。

Q：RAG 效果不好怎么排查？
评估驱动闭环：先跑评估集出四指标 → 哪个低定位瓶颈 → 回对应环节调（Recall 低调检索召回，Precision 低调排序，Faithfulness 低调防幻觉，Relevancy 低调 prompt）→ 每次只改一个变量，再评估确认。别一次改一堆。

小测验

Q1

DBA Copilot RAG 评估，四个指标里属于生成侧的是？

✓ Faithfulness 和 Response Relevancy 是生成侧。 四指标分两维：检索侧（Context Recall 召回全不全 / Context Precision 排序准不准）评 L05-L07；生成侧（Faithfulness 有没有编 / Response Relevancy 答没答对）评 L08。
为什么不是 Context Recall：Context Recall 查的是检索上下文够不够支撑标准答案，评的是检索全不全。
为什么不是 Context Precision：查相关 chunk 排没排前，评的是检索排序。
记法：带 "Context" 的评检索，不带（Faithfulness/Response）的评生成。

Q2

跑评估发现 Faithfulness 只有 0.62，其他指标都还行。瓶颈最可能在哪？怎么改？

✓ 生成侧幻觉，加强防幻觉四件套。 Faithfulness 低 = LLM 答案里有 claim 无法被检索上下文支撑 = 在编。对应 L08 防幻觉四件套：①指令约束（只依据上下文）②引用要求 ③低温度 ④结构化输出。
为什么不是换 embedding：那是检索召回（Context Recall）的解法，Faithfulness 是生成侧问题。
为什么不是 rerank：rerank 调排序（Context Precision），不防幻觉。
为什么不是扩评估集：扩样本不改变指标反映的瓶颈，0.62 是问题不是噪声。
注意：要先确认 Context Recall 也不低——若检索就没召回相关内容，LLM 巧妇难为无米之炊也会"编"，那时根因其实在检索。但题设"其他指标都还行"，所以是生成侧。

Q3

POC 启动，客户催着出效果。以下做法最合理的是？

✓ 先造评估集，再跑基线迭代。 评估集是评估的前提——没评估集跑不出指标，调参是瞎调。50 条高质量评估集（标注相关文档 ID + 部分标准答案）是 POC 第一步，比调参重要。
为什么不能凭感觉调：跑几个 case 看感觉会被 fluency illusion 骗——文字看着通顺但检索可能没命中。要数字说话。
为什么不能只靠 RAGAS 全自动：RAGAS 的检索指标用 LLM-as-Judge 不够准，有标注用传统指标（Recall@K/MRR）更准更便宜；且 Context Recall 需要标准答案，得人工造。
为什么不能先做界面：demo 界面好看但效果差更丢人，售前 POC 核心是效果有数字支撑，不是界面。

Q4

关于 LLM-as-a-Judge，以下不是其已知局限的是？

✓ "需要大规模人工标注"不是 LLM-as-Judge 的局限，恰恰相反。 LLM-as-Judge 的核心价值就是省掉大规模人工标注——用 LLM 自动拆 claim、判断能否被支撑，部分指标（Faithfulness/Response Relevancy）连标准答案都不需要。这才是 RAGAS 在 POC 流行的原因。
其他三项都是真局限：verbosity bias（偏好长答案）、self-enhancement（偏好自己风格）、不稳定（同输入两次分数不同）。
售前要点：LLM-as-Judge 的真正局限是"判断有偏差和不稳定"，不是"要人工标注"。缓解办法：用更强模型评、固定 seed/低温、人工标注校准集校准。

你现在能讲清楚：RAG 四大评估指标（Context Recall/Precision + Faithfulness/Response Relevancy）分别查什么、对应哪个环节、低了怎么改；Faithfulness 和 Context Recall 的对称区别；RAGAS 的 LLM-as-Judge 价值与局限；评估集怎么造、为什么比调参重要；评估驱动优化闭环。M4 生成与质量收口，整个质量体系（L05-L09）闭环完成。下一节进 M5 实战——用 Dify 搭 DBA Copilot RAG demo，把 L01-L09 的概念端到端跑通。
