怎么做

每题给一个 RAG 故障症状，判断根因最可能在 9 个环节的哪一步。点击选项后看详细解释——重点看为什么不是其他环节，那是建立直觉的关键。症状和根因常常不在同一环节，这正是排查最难的地方。

场景 1

DBA Copilot 上线后，用户问「慢 SQL 怎么处理」，系统召回了「慢 SQL 的现象描述」片段，但回答里完全没有处理步骤。你检查发现召回率指标正常，相关文档确实在库里。

✓ 文档切分。 手册的「现象 / 原因 / 处理步骤」被切到了不同 chunk。问处理步骤时，只召回到「现象」片段——它确实和"慢 SQL"相关，所以召回率"正常"，但处理步骤在另一个 chunk 里没被召回。

为什么不是检索：召回率正常说明检索没漏（在切分给定的片段边界内它尽力了）。为什么不是生成：LLM 拿不到处理步骤的上下文，巧妇难为无米之炊，不是它的问题。

口诀：召回率正常但答案残缺，先怀疑切分割裂了语义完整单元。

场景 2

RAG 回答参数类问题总是出错或编造。你查知识库发现：运维手册里关键参数说明在表格里（参数名 / 默认值 / 含义），但这些表格在库里变成了断断续续的乱码碎片。

✓ 文档解析（环节①，最靠前）。 PDF/HTML 里的表格在解析时结构丢失，变成散落文本。切分拿到的是残缺碎片，后面全错。

为什么不是切分：切分基于解析后的文本，解析就错了，切分再聪明也没用——这是"上游污染下游"。为什么不是向量化：embedding 编码的就是残缺碎片，再好的模型也救不回丢失的表格结构。

口诀：表格/公式/图片类内容出错，先查解析（①），它比切分更上游。运维手册表格多，这块尤其要盯。

场景 3

团队用了一个通用英文 embedding 模型处理中文运维语料。用户问「会话 inactive 怎么排查」，库里明明有「会话状态分析」文档，但 Top5 全是不相关内容，相关文档排到 50 名外。

✓ 向量化（embedding 选型）。 中文运维语料用英文通用模型，语义空间不对——「会话 inactive」和「会话状态分析」在人看来是同主题，但在英文模型的向量空间里距离很远。模型把文本映射到了错误的空间。

为什么不是检索：检索只是按向量距离取近邻，向量本身算错了，检索无能为力（它不会"纠正"向量）。为什么不是切分：文档完整、切分合理，问题在把文本变成向量这一步。

口诀：召回大面积跑偏（不是个别漏），且语种/领域特殊，先查 embedding 选型。中文运维场景选 BGE-m3 / GTE-Qwen2 这类中文强的模型。

场景 4

相关知识分散在 8 个 chunk 里。系统检索只取 Top3，总有相关 chunk 没进上下文，答案老是缺这缺那。改成 Top10 后答案明显变全。

✓ 向量检索（K 设置太小）。 Top3 的候选池太小，相关 chunk 根本没机会进入。增大 K 让候选变全，问题缓解。

为什么不是 rerank：rerank 是对已召回的候选精排，候选都不够（只召回 3 个），rerank 没素材可排。为什么不是上下文组装：组装基于检索给的结果，检索给的不够，组装也补不出来。

注意：增大 K 会引入更多噪声 chunk，所以通常配合 rerank 精排——先广召回（大 K），再精排序（rerank 选 Top-N）。这是 ⑤⑥ 协作的典型模式。

场景 5

检索 Top10 里第 1、3、8 个 chunk 是相关的，但 LLM 主要参考了前几个，第 8 个相关 chunk 没被有效利用，答案漏了关键点。你查了召回率，其实够用。

✓ 重排模型（缺 rerank）。 相关 chunk 在 Top10 里但排第 8，LLM 受「Lost in the Middle」影响没重视它。加 rerank（Cross-encoder）把相关 chunk 精排到前 2-3 名。这就是 rerank 让 Top3 命中率从 68%→89% 的意义——把"召回到但排后"的拽到前面。

为什么不是检索：召回没问题（相关 chunk 在 Top10 里），是排序质量问题。为什么不是生成：LLM 没有"自动重排上下文"的能力，它倾向关注首尾，排第 8 就是容易被忽略。

口诀：召回够、排得差、答案漏关键点 → 上 rerank。

场景 6

检索召回了正确文档、也排在前面，但 LLM 回答时不引用文档，还混入了训练数据里的过时信息（比如旧版本的参数名）。

✓ 生成环节（prompt 工程）。 检索给对了，但 prompt 没约束 LLM「只能基于上下文回答 + 必须引用来源 + 不知道就说不知道」，LLM 就自由发挥，混入训练记忆里的旧知识。

为什么不是上下文组装：上下文给的是对的（正确文档排前面）。为什么不是 rerank：排序没问题。

解法：prompt 加引用约束 + 结构化输出（如 JSON）+ 「若上下文无依据则回答"文档未提及"」。这是 L08 Prompt 工程的重点。

口诀：召回排前都对，但答案跑偏/不引用/混旧知识 → 生成环节的 prompt 没约束好。

排查口诀（带走这个）

症状 → 环节 速查
  1. 召回不到（相关文档没进 Top-K）→ 切分 / 解析 / embedding / 检索 K
  2. 召回率正常但答案残缺 → 切分割裂了语义（场景 1）
  3. 表格/公式类内容错乱 → 解析（①，最上游）（场景 2）
  4. 大面积召回跑偏 + 语种/领域特殊 → embedding 选型（场景 3）
  5. 召回够、排得差、漏关键点 → 上 rerank（场景 5）
  6. 召回排前都对，但答案跑偏/不引用/混旧知识 → 生成 prompt（场景 6）
  7. 说不清哪坏 → 评估先行，分环节量化定位（别上来换模型）

核心心法：症状在 ⑧（生成），根因常在 ②（切分）。先沿流水线从上游往下游排查，而不是反向。

✓ 做完 6 题

不管对了几题，关键是把"为什么不是其他环节"想通了。排查直觉就是从这种反向排除里长出来的。错题比对的更有价值——回头看对应场景的反馈解释。
