元数据与结构化抽取

给 chunk 贴标签——用结构化字段补向量检索的盲点

← 上一节：切分策略 下一节：Embedding 选型 →

纯向量检索的盲点

L03 把 chunk 切对了，但检索还是会出一种「语义对、但不对版」的错。看个运维场景：

痛点场景

知识库里 GaussDB 和 PostgreSQL 两套手册都有「慢 SQL 诊断」。用户问「GaussDB 慢 SQL 怎么诊断」，纯向量检索 Top-3 返回了 2 个 PostgreSQL 的文档——因为两边「慢 SQL」的语义实在太像了，embedding 分不开。

问题不在 embedding 弱，也不在切分坏，而在纯向量检索只看语义相似度，看不到「这个 chunk 属于哪个产品」。向量检索是「找最像的」，但运维场景往往要先「找对的范围」再「找最像的」。这个「范围」就是元数据（metadata）。

类似盲点还有：检索出过期版本的参数说明、检索出用户没权限看的敏感处理流程、检索出故障排查章节里的部署内容。这些都是语义相似但「属性不对」。

元数据是什么

元数据是chunk 级的结构化标签，和向量一起存进向量库。检索时不只比对向量，还能按这些字段过滤。

关系库类比（你有数据库背景，这块好懂）

向量库里的一个 chunk ≈ 一行记录：向量是「全文索引」（语义相似度检索），元数据是「字段索引」（精确等值/范围过滤），metadata 过滤就是 WHERE 条件。RAG 检索 = 「WHERE product='GaussDB' + 全文相似度 ORDER BY」组合查询。

pgvector / Milvus / Qdrant 都原生支持 metadata 过滤——存向量时把元数据放进 payload 字段，检索时带过滤条件[2]。

metadata 过滤：pre vs post

过滤和向量检索的先后顺序很关键，分两种：

pre-filtering（先过滤再检索）post-filtering（先检索再过滤）
做法先 WHERE 圈出候选集，再在候选集里向量检索先向量检索 Top-K，再 WHERE 筛掉不合格的
运维类比先 WHERE product='GaussDB' 再全文搜先全文搜 Top-20 再 WHERE 筛
风险候选集太小时召回不足Top-K 不够 → 过滤后结果太少甚至空
推荐⭐ 推荐（候选集够大时）候选集很小时才考虑
post-filtering 的坑

假设 Top-20 里有 15 个是 PostgreSQL 的，post-filter product=GaussDB 后只剩 5 个 GaussDB chunk——结果太少。更糟的是若 Top-20 全是 PG，过滤后直接空，用户以为知识库没有答案。pre-filtering 先把范围缩到 GaussDB，再在里面找最相似的，不会有这问题。

结构化抽取：元数据从哪来

元数据不是凭空有的，得从文档里抽。两种方式：

① 规则抽取（优先用）

从文档自带的结构信息直接读，成本低、稳定、不抽错：

  • 文件路径：/docs/gaussdb/v8.0/慢SQL诊断.md → product=GaussDB, version=v8.0, section=慢SQL诊断
  • 标题层级：Markdown 的 # / ## → section 字段
  • frontmatter：文档顶部的 YAML product: GaussDB → 直接读
  • 文件名 / 目录约定：install-guide.md → doc_type=安装手册

② LLM 抽取（兜底）

文档没有结构信息（扫描件、纯文本导出）时，让 LLM 读 chunk 内容抽出产品/版本/类型。贵且可能抽错，非结构化文档才用。可加校验（规则校验 LLM 抽出的产品名是否在白名单内）。

抽取原则

能用规则就用规则——路径、标题、frontmatter 是免费且零误差的元数据源。LLM 抽取只在规则拿不到时兜底。POC 阶段先把规则抽取跑通，覆盖 80% 场景，再考虑 LLM 补剩余。

运维知识库的元数据字段设计

这是你最需要的实操。运维知识库该抽哪些字段：

字段值示例来源过滤作用
productGaussDB / PostgreSQL / MySQL路径 / 标题防跨产品误召回（痛点场景）
versionv8.0 / v9.0路径 / 标题防过期文档
doc_type安装手册 / 故障排查 / 参数说明标题 / LLM按需检索（只查故障库）
section慢SQL诊断 / 会话分析标题层级精确定位章节
effective_date2024-06-01文档元信息时效过滤（只要最新）
permissionpublic / dba_only文档分类权限控制（不返回越权内容）
source_urlhttps://...文档来源引用追溯（生成答案时附链接）
售前视角

元数据字段设计是售前方案里的「数据治理」环节，客户最爱问「你们怎么保证不返回过期/越权内容」。能讲清 metadata 过滤 + permission 字段，是方案成熟度的体现。

面试视角

Q：metadata 过滤为什么优先 pre-filtering？ post-filtering 可能因 Top-K 不够导致过滤后结果太少甚至空；pre-filtering 先把范围缩到合规候选集，再向量检索，保证召回质量。类比关系库：先 WHERE 再 ORDER BY 全文相似度。

Q：元数据抽取用规则还是 LLM？ 能用规则就用规则（路径/标题/frontmatter），成本低、稳定、零误差；非结构化文档才用 LLM 兜底，贵且可能抽错。POC 先规则覆盖 80%。

Q：metadata 过滤和混合检索（L06）什么关系？ 两者正交、可叠加。混合检索解决「用什么方式召回」（向量+BM25），metadata 过滤解决「在哪个范围里召回」（产品/版本/权限）。一个完整检索 = metadata 过滤圈范围 + 混合检索召回 + rerank 精排。

小测验

场景

知识库含 GaussDB 和 PostgreSQL 两套手册。用户问「GaussDB 慢 SQL 怎么诊断」，纯向量检索 Top-3 返回了 2 个 PostgreSQL 的慢 SQL 文档（语义太相似）。最佳改进是？

✓ 加 product 元数据 + pre-filter。 根因是纯向量检索看不到「产品」这个结构化属性。GaussDB 和 PostgreSQL 的慢 SQL 语义本就极相似，靠 embedding 硬分不开也没必要——用 metadata 过滤把范围先缩到 GaussDB，又准又稳，还省算力。

为什么不是「换更强 embedding」：语义确实相似，强行让 embedding 把同主题不同产品的文档拉开，反而会损害「跨产品类比检索」的能力（有时用户就是想看 PG 的做法借鉴）。而且这是结构化属性，用结构化过滤比用向量硬区分更可靠。
为什么不是「增大 Top-K」：候选里 GaussDB 还是少数，增大 K 只是多塞几个 PG 文档，没解决产品边界，还增 rerank 成本。
为什么不是「加 rerank」：rerank 能把 PG 文档降权，但治标不治本——PG 文档还是占着 Top-K 名额，挤掉本该进来的 GaussDB 文档。pre-filter 直接把 PG 挡在候选外。

口诀：结构化属性（产品/版本/权限）用 metadata 过滤，语义相似度用向量——别让向量干它不擅长的事。

✓ 本节胜利

你现在掌握了：

  1. 纯向量检索的盲点——语义相似但「属性不对」（产品/版本/权限/时效）。
  2. metadata 过滤 = WHERE 条件，pre-filtering 优先，post-filtering 有坑。
  3. 抽取原则——规则优先（路径/标题/frontmatter），LLM 兜底非结构化文档。
  4. 运维元数据字段设计——7 个字段表，售前能讲「数据治理」。
  5. 完整检索的三层——metadata 过滤圈范围 + 混合检索召回 + rerank 精排（为 L06/L07 铺路）。
