为什么有这一节

L10 用 Dify 搭了运维知识库 RAG demo——那是平台封装式：建库/分段/检索都配成表单。这节换 n8n，它是工作流编排式：RAG 不是开箱功能，要用「Advanced AI」节点拖拽连线拼一条 pipeline。

两条路线概念完全对应（L03 分段 / L05 embedding / L04 向量库 / L06 检索 / L08 生成），只是拼装界面不同。学完这节你能讲清：同一个 RAG，Dify 和 n8n 各自怎么落地、差在哪、什么场景选哪个——售前常见问题。

本节定位

云端测试为主，不碰 GaussDB 适配（那是另一条线）。用 n8n 官方托管 + 云端向量库（MongoDB Atlas）+ OpenAI API，最快跑通一个可聊天的运维 RAG。跑通后再考虑换组件（如 OpenAI 换 bge-m3、MongoDB 换 GaussDB）。

模板来源：n8n 4827 · n8n 5148

4827 模板的 RAG 架构（拆给你看）

模板实际是两个 workflow（摄入 + 问答），概念你全学过，只是换了实现：

Workflow 1：文档摄入（ingestion）

Google Docs(文档源) → Text Splitter(分块) → OpenAI Embeddings(向量化)
  → MongoDB Atlas Vector Store(存向量+元数据)

Workflow 2：聊天问答（query）

WhatsApp(用户消息) → OpenAI Embeddings(查询向量化)
  → MongoDB Vector Search(相似度检索)
  → Knowledge Base Agent(检索结果+system prompt → GPT-4o-mini)
  → Memory Buffer(多轮记忆) → WhatsApp(回消息)

关键洞察

骨架和 L10 Dify demo 完全一样，只是每个环节换了实现。n8n 把 Dify 藏在表单背后的环节显式暴露成节点——你能看见 Text Splitter、Embeddings、Vector Store 是分开的节点各自可换，这是 n8n 比 Dify 灵活的代价（要懂概念）也是收益（每环节可换）。

改造路线：4 处替换

直接照搬 4827 跑不了运维 demo，要改 4 处：

① WhatsApp → Chat Trigger（最省事）

WhatsApp 要 Meta 企业认证 + 绑手机号 + 审核几天，测试阶段不值得。删掉 WhatsApp 节点，换成 n8n 自带 Chat Trigger（网页聊天框，点开就能聊，零认证）。功能等价。

② Google Docs → 上传 4 篇运维 md

把文档源从 Google Docs 换成 L10 用的那 4 篇运维文档（慢SQL/会话锁/连接管理/参数调优）。用 Document Loader 节点上传本地文件，或先读文件内容塞进节点。

③ 模型换国内云 API（智谱，替代 OpenAI）

4827 原配 OpenAI（GPT-4o-mini + text-embedding-ada-002 1536 维）。没有 OpenAI key 可换国内厂商——n8n 的 LLM/Embeddings 节点提供商无关，能换后端。本节用智谱（一个平台一个 key 搞定 LLM + Embedding，且 GLM-4-Flash 免费）：

组件4827 原配本节换成维度
LLMOpenAI GPT-4o-mini智谱 GLM-4-Flash（免费）/ GLM-4—
EmbeddingOpenAI ada-002智谱 embedding-21024

换法：n8n 里把 OpenAI Chat Model 节点换成 OpenAI 兼容节点指向智谱 API（智谱 API 兼容 OpenAI 格式，base_url 填 https://open.bigmodel.cn/api/paas/v4），或直接用支持智谱的节点；Embeddings 节点同理。凭证在 n8n Credentials 里加智谱 API key。

维度变了 → MongoDB 索引必须跟着改

OpenAI 1536 维换成智谱 1024 维，MongoDB Atlas 向量索引 numDimensions 必须从 1536 改成 1024，否则检索报错。这是换 Embedding 模型最容易踩的坑——Embedding 模型决定索引维度。

Embedding 按字符量计费（智谱约 0.5 元/百万 token），4 篇运维文档向量化成本几分钱，查询每月几毛钱，非成本顾虑点。GLM-4-Flash 有免费额度。

④ system prompt → DBA Copilot prompt

在 Knowledge Base Agent 节点的 system prompt 里，换成 L10 那个 DBA Copilot prompt：

你是 GaussDB 资深 DBA，基于知识库回答故障诊断问题。
规则：①只依据上下文 ②不足就说"无法诊断，建议联系..." ③标注引用 ④步骤具体可执行。

温度设 0.2。

一个要记住的约束（后续换 GaussDB 时）

4827 用 OpenAI 1536 维存 MongoDB，MongoDB 没维度上限所以能跑。但你要后续把这个 RAG 搬到 GaussDB（你的适配目标），GaussDB 向量维度硬上限 1024（见 GaussDB 改造方案 2.2）——届时 OpenAI 1536 维不可用，要换 ≤1024 维模型（bge-large-zh 1024 / bge-base 768）。云端测试阶段先用 OpenAI 跑通，换库时再换模型。

云端部署：n8n Cloud + MongoDB Atlas

三样东西，都有免费档够测试：

1. n8n Cloud（官方托管 n8n）

  • 注册 n8n Cloud，选 Starter 档（有免费试用）
  • 不用自己部署 n8n，登进网页就能拖节点
  • 这是最省事的云端 n8n 方案

2. MongoDB Atlas（云托管向量库）

  • 注册 MongoDB Atlas，免费档 M0 够测试
  • 建一个 database + collection（存 embedding 和元数据）
  • 建向量搜索索引（关键）：索引名 data_index，类型 knnVector，维度 1024（对齐智谱 embedding-2），相似度 cosine
// MongoDB Atlas 向量索引定义（JSON）—— 维度对齐智谱 embedding-2 = 1024
{
  "fields": [{
    "type": "vector",
    "path": "embedding",
    "numDimensions": 1024,
    "similarity": "cosine"
  }]
}
易踩坑：索引名 + 维度都要对齐

① 索引名：4827 模板里 MongoDB Vector Search 节点写死了 data_index，你在 Atlas 建的必须叫这个名，否则检索报错。两个 workflow（摄入+问答）的 MongoDB 节点要连同一个 collection、同一个索引名。

② 维度：索引 numDimensions 必须等于你 Embedding 模型输出维度。本节用智谱 embedding-2 = 1024（不是 4827 原配 OpenAI 的 1536）。换模型必查维度，索引和模型不一致必报错。

3. 智谱 API key（LLM + Embedding）

  • 注册 智谱开放平台，拿 API key
  • GLM-4-Flash 免费（有额度），Embedding 也有免费额度
  • 在 n8n 的 Credentials 里加智谱凭证；智谱 API 兼容 OpenAI 格式，可用 OpenAI 兼容节点配 base_url https://open.bigmodel.cn/api/paas/v4

5 步跑通

  1. 开 n8n Cloud + 导入模板：登 n8n Cloud → 点 4827 页面的 "Use for free" → 导入到你 n8n
  2. 配 3 个凭证：在 n8n Credentials 加 智谱 API key + MongoDB Atlas 连接 + （Google Docs 如保留则加，否则换成 Document Loader 上传 md）
  3. 改 4 处：WhatsApp→Chat Trigger / Google Docs→4篇运维md / OpenAI 节点换智谱（LLM + Embedding）/ system prompt→DBA prompt
  4. 跑 Data Ingestion：先执行摄入 workflow，4 篇文档向量化写入 MongoDB（检查 collection 里有没有数据、embedding 字段在不在）
  5. 跑 Chatbot 测试：用 L10 那 4 个召回测试问题问，验证检索准不准 + 答案有没有标引用
召回测试题（复用 L10）

用这 4 个问题各问一遍，看检索命中和生成质量：

  • 「数据库突然变慢，怎么定位慢SQL？」→ 应命中文档1
  • 「应用卡住报超时，怎么查锁等待？」→ 应命中文档2
  • 「报 too many connections 怎么办？」→ 应命中文档3

n8n vs Dify：售前怎么选

维度Dify（L10）n8n（本节）
定位AI 应用平台，RAG 内置工作流引擎，RAG 拼装
搭 RAG5 步配置表单拖节点连线
灵活度低（平台封装）高（每环节可换节点）
上手快，不懂 LangChain 也能用要懂 LangChain 概念
向量库选项内置 + 几种后端Vector Store 节点支持 Pinecone/Qdrant/pgvector/MongoDB 等
多系统编排弱（专注 AI 应用）强（n8n 老本行）
适合场景纯 RAG 应用 / 快出 demoRAG + 外部系统联动（如 WhatsApp/Slack/CRM）
选型口诀

纯 RAG 出 demo → Dify（快、封装好）；RAG 要和外部系统编排（消息/工单/CRM 联动）→ n8n（编排是老本行）。4827 模板就是个例子——它把 RAG 和 WhatsApp 编排在一起，这种"RAG + 消息渠道"的场景 Dify 做起来费劲，n8n 天然合适。

n8n 能做什么 / 不能做什么（边界，售前要讲清）

  • 能：拖拽拼 RAG pipeline / 每环节换节点（换向量库/换模型/换 LLM）/ 编排外部系统（WhatsApp/Slack/HTTP）/ 多轮记忆（Memory 节点）/ 引用展示（Agent 节点配 prompt）
  • 不能（或不便）：不内置 RAGAS 评估（要外接，同 Dify）/ 不内置 reranker 模型（rerank 要应用层另接或靠向量库自带）/ 不像 Dify 有"召回测试"可视化面板（n8n 要手动跑节点看检索结果）/ 混合检索要自己拼两路节点（Dify 一键开关）

从 demo 到 POC：后续可换的组件

跑通云端 demo 后，每个节点都能换，对应你的真实落地需求：

  • OpenAI → bge-m3：Embeddings 节点换 Ollama 或自部署的 bge-m3，维度 ≤1024，为搬 GaussDB 做准备
  • MongoDB Atlas → GaussDB：Vector Store 节点换 pgvector 适配器指向 GaussDB（见 GaussDB 改造方案）
  • 加 reranker：在检索和生成之间插一个 HTTP Request 节点调 bge-reranker（L07）
  • 加评估：外接 Langfuse/LangSmith 记录检索和生成，跑 RAGAS（L09）
和 GaussDB 适配工作的关系

本节云端 demo 用 MongoDB Atlas，不碰 GaussDB。但跑通后你会对"RAG 每环节怎么换组件"有手感——这正是你做 GaussDB adapter（search_by_vector / search_by_full_text）时要的理解：每个节点对应一个可替换的接口契约。4827 的 Vector Store 节点 = 你在写的 vdb-gaussdb adapter 要实现的能力。

本节胜利

跑通后你掌握：

  • n8n 用 Advanced AI 节点拼 RAG pipeline 的完整流程
  • 同一个 RAG，Dify（平台式）和 n8n（编排式）各自怎么落地、差在哪、怎么选
  • 云端测试最小路径（n8n Cloud + MongoDB Atlas + OpenAI，都有免费档）
  • 每个环节可换组件的手感——为 GaussDB 适配打基础
