Rerank 重排：检索够"全"之后，让它够"精"

两阶段检索——bi-encoder 粗召回 + cross-encoder 精排，把噪声踢出 Top-5

← 上一节：混合检索 下一节：上下文组装 →

动机：recall 够了，precision 还差

L06 混合检索把 recall@5 推到 88%——相关文档基本都捞进来了。但你打开 Top-5 看一眼，里面还混着 1-2 个噪声 chunk（字面命中了关键词但答非所问）。问题已经不在"漏捞"（recall 够了），而在排序不准——bi-encoder 粗排把无关的排进了 Top-5，LLM 拿到的上下文不够精。

Rerank 就来解决这个：用一个更精的模型对 Top-50 重新打分排序，把真正相关的挤进 Top-5，噪声踢出去。

一句话定位

检索负责多捞（recall，别漏），rerank 负责精挑（precision，别杂）。两阶段分工。

核心：两阶段检索

RAG 检索拆成两步，用不同模型：

query
  │
  ▼
阶段1 检索（粗）  bi-encoder 扫全库 → Top-50     ← 快，可预计算
  │
  ▼
阶段2 Rerank（精） cross-encoder 重排 Top-50 → Top-5  ← 精，只跑50个
  │
  ▼
喂给 LLM
  • 为什么不全用 cross-encoder？ 全库 5 万篇，每对 query-doc 都要跑一次 cross 模型，慢到没法用（秒级起步）。
  • 为什么不全用 bi-encoder？ 排序粗，Top-5 混噪声，LLM 上下文不精。
  • 两阶段的本质：便宜模型（bi）干粗活（扫全库），贵模型（cross）干精活（只跑 50 个）。和 DBA 思路一样——先用索引粗捞 50 行，再对 50 行做复杂排序，不可能对全表做复杂排序。

bi-encoder vs cross-encoder：为什么 cross 更精

这是 rerank 的核心原理，面试高频。两者的根本区别在query 和 doc 有没有"交互"。

bi-encoder（双塔）cross-encoder（交叉）
架构query 和 doc 分别过 transformer，各自编码成向量query 和 doc 拼一起过同一个 transformer
交互无——各自编码时看不到对方有——注意力让 query 每个词看 doc 每个词
输出两个向量，算 cosine直接输出一个相关性分数
预计算doc 向量入库时算好，查询只编码 query不能预计算——query 来了才能拼一起算
速度快（查询只算 1 个向量 + ANN 检索）慢（每对 query-doc 跑一次模型）
精度粗精
用在哪检索阶段（扫全库）Rerank 阶段（只对 Top-50）

为什么"交互"这么关键

query = "ORA-01555 怎么处理"，doc = "快照太旧：回滚段不足导致无法构造一致性读"。

  • bi-encoder：query 和 doc 各自编码成向量。字面无重叠（"ORA-01555" vs "快照/回滚段"），靠模型预训练时学到的语义联想——如果训练语料没怎么见过 ORA-01555，cosine 就不高，相关 doc 排不进 Top-5。
  • cross-encoder：拼一起喂模型，注意力机制让 ORA-01555 直接"看到"快照太旧和回滚段，能学到词级关联——哪怕字面不重叠，也能打出高分。
类比

bi-encoder 像两人各自写简历给中介匹配——快（简历可存档），但中介只看简历，匹配粗。cross-encoder 像两人面对面聊，每句话都能即时反应对方——精，但慢（必须两人都在场才能聊）。

Rerank 模型选型

主流用 BAAI 的 bge-reranker 系列（中文友好、本地可部署，和 BGE-M3 一脉）：

模型参数量语言适用
bge-reranker-v2-m3568M多语含中文运维场景首选：轻量、中文好、本地可跑
bge-reranker-v2-gemma2B多语更强但大，资源充足、精度要求高时
bge-reranker-large（v1）560M多语老版，v2-m3 出来后少用
bge-reranker-base（v1）278M多语更小，POC 试水
LLM-based rerank——用 LLM 打分，贵且精度不稳，不推荐生产
选型结论

运维 RAG（中文 + 本地 + 轻量）→ bge-reranker-v2-m3。和 embedding 模型（BGE-M3）是两个独立模型，别混：embedding 入库时用（生成向量），rerank 查询时用（重排打分）。rerank 模型不入库，查询时实时跑。

Top-K 怎么定：K1 和 K2

两阶段有两个 K，分别管"粗捞多少"和"精排留多少"：

  • K1（粗召回数）：检索阶段召回多少。常见 50-100。recall@K1 是 rerank 的天花板——相关文档没进 Top-50，rerank 再精也救不回。看 recall@K 曲线拐点定。
  • K2（精排输出）：rerank 后留多少喂 LLM。常见 5-10。看 LLM 上下文窗口和精度需求。
K1 的陷阱

K1 太小 → recall 上限低（相关文档根本没捞进来，rerank 无米下锅）；K1 太大 → rerank 慢（要跑更多对）且噪声多。经验起步：K1=50, K2=5，按评测调。

和混合检索的配合：三层递进

把 L05-L06-L07 串起来，RAG 检索的完整 pipeline：

query
  │
  ├─→ dense（BGE-M3 向量）──┐
  │                          ├─→ RRF 融合 → Top-50
  └─→ sparse（BM25/BGE-M3）─┘
                                │
                                ▼
                          Rerank（cross-encoder）→ Top-5
                                │
                                ▼
                            喂 LLM
  • recall 靠混合（dense + sparse 广召回 50 个，别漏）
  • precision 靠 rerank（cross-encoder 精排 5 个，别杂）
  • 三层递进升级路径：纯 dense → 混合（提 recall）→ +rerank（提 precision），评测驱动逐步加，不要一上来全开。

68% → 89% 的真相（面试高频）

L05 提过"加 rerank 后 recall@5 从 68% 涨到 89%"。这数字怎么来的，必须搞懂——面试必问。

假设评测集上：

  • recall@50 = 95%：相关文档基本都在 Top-50 里（检索没漏，混合检索干得好）
  • recall@5 = 68%：但 bi-encoder 排序粗，相关文档虽然进了 Top-50，却没排进 Top-5
  • 加 rerank 后 recall@5 = 89%：cross-encoder 重排，把原本在 Top-50 但没进 Top-5 的相关文档挤进了 Top-5
本质（必背）

rerank 提的是"窄窗口 recall"——把宽窗口（Top-50）里的好东西排进窄窗口（Top-5）。这等价于提 precision@5（窄窗口里相关的比例高了）。rerank 不增加召回，只改善窄窗口的排序。它是"排序优化器"，不是"召回扩展器"。

关键前提

rerank 能提 recall@5 的前提是 recall@50 够。如果相关文档压根没进 Top-50（recall@50=60%），rerank 再强也救不回——得先治检索（混合/切分/embedding），别指望 rerank 捞回漏召的。诊断顺序：先看 recall@K1 够不够，不够治检索；够了再看 recall@5/precision@5，不够才上 rerank。

成本与延迟

  • 延迟：rerank 50 个 doc，bge-reranker-v2-m3 在 GPU 上约 30-80ms，CPU 上几百 ms。加一跳延迟，换 Top-5 精度。
  • 批处理：rerank 可批量（一次喂多个 query-doc pair 进模型），比逐个跑快得多。
  • 部署：多部署一个模型（rerank 模型独立于 embedding 模型），多一份显存/内存。
  • 何时上（呼应 L02 优化优先级）：rerank 是中等成本，排在切分/prompt（廉价）之后、换 embedding（最贵）之前。检索 recall 达标、precision 不够时才上。

运维实战：什么时候上 / 不上 rerank

场景动作
recall@50 够，recall@5 / precision@5 不够✅ 上 rerank，正解
recall@50 不够（相关文档没召回）❌ 先治检索（混合/切分/embedding），rerank 救不回漏召
POC 早期，切分/检索还没调好❌ 先治廉价环节（切分/prompt），rerank 放后面
延迟预算极紧（<50ms 端到端）⚠️ rerank 加一跳，权衡或用更小模型
精度要求高、延迟可接受✅ 上 rerank，甚至用 gemma 大模型
踩坑提醒

① rerank 模型 ≠ embedding 模型，两个独立模型，别混；② rerank 不入库（查询时实时跑，不预计算）；③ rerank 不增加召回，别用它治"漏召"——那是混合检索的活。

调参清单

  • K1（粗召回）：50-100，看 recall@K1 曲线拐点
  • K2（精排输出）：5-10，看 LLM 上下文窗口
  • rerank 模型：中文场景 bge-reranker-v2-m3，资源紧用 base，精度高用 gemma
  • batch size：rerank 批处理降延迟，按显存调
面试视角 · 高频问题

Q：rerank 提 recall 还是 precision？
提"窄窗口 recall"（把 Top-50 的好东西排进 Top-5）= 提 precision@5。不增加召回，前提是 recall@K1 够。

Q：为什么两阶段，不全用 cross-encoder？
速度。cross 不能预计算，全库跑不动。bi 可预计算 + ANN 索引，毫秒扫全库。

Q：cross-encoder 和 bi-encoder 区别？
交互（cross 拼一起有注意力，bi 各自编码无交互）、预计算（bi 可 cross 不可）、精度（cross 高）、速度（bi 快）。

Q：rerank 在 pipeline 哪环？
retrieve 之后、generate 之前。

Q：recall@K1 不够时怎么办？
先治检索（混合/切分/embedding），rerank 救不回漏召。

小测验

Q1

混合检索 recall@50 = 60%，recall@5 = 55%。团队想加 rerank 把 recall@5 提到 85%。能成吗？

✓ 不能。rerank 只能重排已召回的文档，不增加召回。recall@50=60% 意味着 40% 相关文档压根没进 Top-50，rerank 再精也排不进 Top-5。recall@K1 是 rerank 的天花板。先治检索（混合/切分/embedding）把 recall@50 提上去，再谈 rerank。

Q2

为什么 RAG 检索不全用 cross-encoder（一步到位精排）？

✓ 速度问题。cross-encoder 把 query 和 doc 拼一起过模型，doc 向量不能预计算——query 来了才能算。5 万篇全库跑 cross 要几秒甚至几十秒。所以用两阶段：bi 预计算 + ANN 粗扫全库到 Top-50，cross 只对 50 个精排。便宜模型干粗活，贵模型干精活。

Q3

rerank 上线后 recall@5 从 68% → 89%。这"涨出来的 21%"来自哪？

✓ 排序优化，不是召回扩展。前提是 recall@50 够（相关文档在 Top-50 里）。bi-encoder 粗排把相关的排到了 6-50 名，没进 Top-5；cross-encoder 精排把它们重排进了 Top-5，所以 recall@5 涨了。rerank 是排序优化器，不是召回扩展器——没多捞任何文档，只改善窄窗口的排序。

Q4

运维 RAG，中文文档，本地部署，embedding 用 BGE-M3。rerank 模型选型 + 它和 embedding 模型的关系？

✓ bge-reranker-v2-m3，两个独立模型。中文+本地+轻量 → v2-m3。gemma 更强但 2B 太大，运维场景没必要。LLM rerank 贵且不稳，不推荐生产。关键认知：rerank 模型 ≠ embedding 模型。BGE-M3 是 embedding（入库时生成向量），bge-reranker 是 rerank（查询时重排打分），各司其职。rerank 不入库，查询时实时跑。

你现在能讲清楚：两阶段检索为什么这么设计（速度+精度权衡）、cross 为什么比 bi 精（注意力交互）、rerank 提的是窄窗口 recall 不是召回、recall@K1 是 rerank 天花板。M3 检索侧三件套（embedding → 混合 → rerank）齐了，接下来 L08 把检索结果喂给 LLM 的上下文组装。
