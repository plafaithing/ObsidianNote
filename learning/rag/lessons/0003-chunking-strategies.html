切分策略：决定 RAG 的上限

五种策略、两个参数、一个铁律——切分必须适配文档类型

← 上一节：全流程地图 下一节：元数据与结构化抽取 →

为什么切分是「决定上限」的环节

前面排查练习里，场景 1（现象/处理步骤被切到不同 chunk）和场景 2（表格被切坏）的根因都在切分。切分是 RAG 流水线里最易被忽视、却决定天花板的一步：

真实踩坑（HugoGu）

企业文档检索，固定 512 token 切分导致表格被截断，召回率从 85% 掉到 32%。改用按段落分割 + 200 token overlap 后恢复到 78%[1]。切分一变，召回率天差地别。

原因：切分决定了每个 chunk 的语义完整性。chunk 残缺，embedding 编码的就是残缺语义，检索再准也只找到残缺，rerank 再强也排不出完整信息，LLM 拿到的上下文就是残缺的。下游所有环节都在切分给定的片段边界内工作——这就是「决定上限」的含义。

核心权衡：chunk 大小的两难

所有切分策略都在同一个权衡上做选择：召回精确度 vs 上下文完整性。

chunk 太大chunk 太小
召回一个 chunk 含多个主题，向量被「稀释」，召回精确度下降语义不完整（一句话切断），召回虽精确但信息零碎
上下文完整，但占窗口、增成本残缺，答案容易缺这缺那
典型症状搜到了但夹带不相关内容搜到了片段但答不全（场景 1）

没有「正确」的大小，只有「适配文档类型」的大小。下面五种策略就是不同的折中方式。

五种切分策略

策略怎么做适用优缺点
固定大小按字符/token 数切简单纯文本简单；可能截断语义（表格、句子切两半）
递归分割按段落→句子→字符逐级切通用LangChain 默认，最常用；仍可能割裂跨段语义
语义分割按相邻句 embedding 相似度骤降处切叙述性长文语义边界准；计算开销大
结构化分割按标题/章节切Markdown / HTML 手册保留文档逻辑 ⭐ 运维首选
页面级按页切PDF / 扫描件NVIDIA 评估最稳[4]；粒度粗
进阶：Late Chunking

先对整篇长文本编码、再切分——让每个 chunk 保留全局上下文信息，避免「切完就丢失上下文」。适合长文档，是较新的技术[1]。POC 阶段先用前五种，够用。

两个关键参数

① Chunk 大小

实践经验值：500–1500 tokens（取决于检索粒度）[1]。但这是参考值，不是教条——运维手册按章节切可能一个 chunk 就 2000 token，对话日志可能 200 token 就够。评测驱动：搭个 50 题测试集，不同大小跑 Recall@5，选最优。

② Overlap（重叠）

相邻 chunk 之间重叠一部分文本，避免边界信息被切断。10–20% 的 chunk 大小[1]。比如 chunk 1000 token，overlap 100–200 token。

overlap 不是越大越好

overlap 大能保边界信息，但冗余增加（同一段内容存多份）、存储和检索成本上升、还可能让重复内容多次进 Top-K 挤掉其他相关 chunk。10–20% 是平衡点。

运维文档怎么切（实操）

这是你最需要的部分。运维知识库有三类典型内容，切法不同：

① 运维手册（Markdown / Confluence / HTML）

用结构化分割，按标题层级切。一条「慢 SQL 诊断」章节（含现象/原因/处理步骤）整体作为一个 chunk，不要按固定 token 切断。

## 慢 SQL 诊断          ← 切分边界
### 现象               ← 和下面一起，不切
### 原因
### 处理步骤
  1. 查 PGXC_STAT_ACTIVITY
  2. 看执行计划...
## 会话分析            ← 下一个 chunk

这样用户问「慢 SQL 怎么处理」，召回的 chunk 完整含「现象+原因+处理」，不会出现场景 1 那种残缺。

② 表格（参数说明表、错误码表）

整表保留为独立 chunk，绝不切断。或把表格转成结构化文本（「参数名: 值: 含义」逐行），让 embedding 能编码表格语义。这是场景 2 踩坑的解法——固定 token 切分会把表格切乱。

③ 代码块（SQL 示例、命令）

完整保留，附在所属章节 chunk 里。一段 SQL 切两半毫无意义，检索到半个 SQL 没用。

运维切分铁律

保证「现象 / 原因 / 处理步骤」在同一个 chunk，不割裂；表格、代码块整块保留。这一条做对，切分环节的上限就稳了。

面试视角

Q：chunk 大小怎么定？ 不是定值，取决于文档类型和检索粒度。手册类按结构切（500–1500 token），对话类按语义切。关键是评测驱动——搭测试集跑 Recall@K 选最优，而不是拍脑袋。

Q：overlap 的作用？多大合适？ 避免边界信息丢失，10–20%。太大冗余增成本、重复内容挤掉其他相关 chunk。

Q：切分和 embedding 哪个更重要？ 切分决定上限，embedding 决定在这个上限内的匹配质量。先保证切分别拖后腿（场景 1、2 都是切分拖后腿），再优化 embedding。这个回答能体现系统观。

小测验

场景

运维手册里「慢 SQL 诊断」章节结构是「现象 / 原因 / 处理步骤 / 相关参数表」。团队用固定 256 token 切分后，用户问「慢 SQL 怎么处理」，检索召回了一个只含「现象 + 半个原因」的 chunk，答案严重残缺。最佳改进是？

✓ 改用结构化分割，按章节标题切。 根因是固定 256 token 把「现象/原因/处理」切散了。结构化分割按 ## 慢 SQL 诊断 标题切，整节为一个 chunk，语义完整。

为什么不是「增大到 1024 token」：能缓解（把更多内容塞进一个 chunk），但没解决根因——固定大小仍可能切在章节中间，且会夹带相邻章节噪声。结构化分割才对准了文档的逻辑边界。
为什么不是换 embedding：切分问题，embedding 救不了残缺片段。
为什么不是加 rerank：召回的 chunk 本身残缺，rerank 排序也排不出不存在的信息。

口诀：文档有结构（标题/章节）→ 结构化分割；固定大小只适合无结构纯文本。

✓ 本节胜利

你现在掌握了：

  1. 为什么切分决定上限——下游都在切分给定的片段边界内工作，切分残缺全链路救不回。
  2. 五种策略的取舍——运维手册首选结构化分割，表格/代码块整块保留。
  3. 两个参数——chunk 500–1500 token、overlap 10–20%，评测驱动定值。
  4. 面试能讲切分 vs embedding 的优先级（切分决定上限）。
