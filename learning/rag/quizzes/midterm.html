M1 地基（L01–L02）

Q1团队用 LLM 做数据库运维问答，担心三件事：①模型乱编故障处理步骤 ②新版本参数文档模型没学过 ③内部故障手册是私密的。这三个分别对应 RAG 解决的哪三个痛点？

✓ ①幻觉 ②时效 ③领域。幻觉=乱编（L01）；时效=训练截止后新文档没学过；领域=私域知识模型不掌握。RAG 用检索把外部知识喂给 LLM，三痛同治。
记忆：幻觉（乱说）、时效（过时）、领域（不懂私域）。

Q2客户需求：一份 50 页公开产品手册让 LLM 问答，手册不涉密、不会更新。最经济的方案？

✓ 长上下文。手册公开（不涉密）、静态（不更新）、量小（50 页塞得下）——长上下文最经济，无需建向量库。
RAG 适合：文档量大 / 动态更新 / 私域需检索过滤。L01 的 RAG vs 微调 vs 长上下文取舍：能塞就塞，塞不下或要更新才 RAG。

Q3RAG 答非所问。排查发现：检索召回的 chunk 明明是相关的，但 LLM 生成的答案没用这些 chunk，而是自己编了一套。问题最可能在哪环？

✓ 上下文组装 / Prompt。检索对了（chunk 相关）但生成没用 → 问题在把检索结果喂给 LLM 的环节：prompt 没要求"只依据上下文回答"、没给引用约束、上下文没组装好。这是 L02 木桶效应的环节定位——检索桶板OK，生成桶板漏。

Q4POC 阶段 RAG 效果差，团队提议：①换更强 embedding ②调切分策略 ③加 rerank ④改 prompt。按"廉价优先、先治低成本环节"的正确排查顺序？

✓ ④prompt → ②切分 → ③rerank → ①换 embedding。L02 POC 优化优先级：先治廉价环节（改 prompt、调切分——零成本快试），rerank 中等成本，换 embedding 最贵（要重新向量化整个知识库，L02 说放最后）。
口诀：先廉后贵，先治能快速验证的。

M2 数据侧 Ingest（L03–L04）

Q5运维文档是 Markdown 写的，有清晰标题层级（## 故障诊断 / ### 慢SQL / #### 诊断步骤）。切分策略首选？

✓ 按 Markdown 标题结构化切分。L03：文档有明确结构（标题层级）就用结构化切分，保留语义边界——一个 chunk 对应一个故障/步骤，完整且自包含。固定字数会劈断故障步骤；递归字符次之；语义切分成本高留给无结构文档。

Q6切分时设 overlap（重叠，如 chunk 间重叠 50 字）的作用是？

✓ 防边界信息丢失。L03：overlap 让相邻 chunk 共享一段文本，关键句若被切分边界劈断，仍能在前/后某个 chunk 完整出现，检索时能命中完整语义。代价是存储略增。

Q7运维 RAG，用户问"GaussDB v8.0 的慢SQL诊断"，却返回了 OpenGauss v3.0 的慢SQL文档。最直接的解法？

✓ 元数据过滤。L04：跨产品/版本混淆是元数据过滤的典型场景。embedding 分不清 GaussDB v8.0 和 OpenGauss v3.0（语义都是"慢SQL诊断"），但元数据能精确区分。从文档路径/标题抽 product、version，检索时 WHERE product='gaussdb' AND version='v8.0' 过滤。

Q8元数据抽取"规则抽取优先于 LLM 抽取"，根本原因？

✓ 规则零成本零误差，LLM 贵且会错。L04：文档自带结构（路径/标题/frontmatter）用规则读，免费且准。LLM 兜底无结构文档（扫描件 OCR、纯文本），但要每 chunk 调一次模型（贵）且需 JSON mode + 白名单校验防出错。能用规则就别用 LLM。

M3 检索侧（L05–L06 + Q&A 0006–0010）

Q9中文运维 RAG，文档含大量错误码（ORA-01555）、视图名（PGXC_STAT_ACTIVITY）、参数名。要求本地部署（数据不出域）。embedding 选型？

✓ BGE-M3。L05：中文+本地部署+标识符多 → BGE-M3。中文优化、C-MTEB 高分、1024 维平衡、本地部署数据不出域。OpenAI 中文一般、贵、数据出境（运维敏感）。BGE-M3 还自带稀疏向量，一站式混合检索（L06）。bge-small-en 是英文模型，直接排除。

Q10关于 embedding 维度，以下正确的是？

✓ 维度模型架构定死，不可调。Q&A 0004：维度是模型架构决定的输出维度，选了 BGE-M3 就是 1024、OpenAI large 就是 3072。能"选哪个维度的模型"，不能"给模型调维度"。1024 是运维甜点（Q&A 0007 验证）。768 POC 够用，不是"一定差"。

Q11HNSW 向量检索 Recall@5 不够，调参顺序（从最便宜到最贵）？

✓ ef → efConstruction → M。Q&A 0007：ef（ef_search）检索时动态调，无需重建索引，最便宜，先调；efConstruction 建索引时定，改要重建；M 影响最大也要重建，最后动。都不够才退回查维度/切分。DB 类比：先调查询扫描范围，再动索引结构。

Q12embedding 维度从 1024 升到 3072，对 HNSW 检索的影响？

✓ 三重代价。Q&A 0007：①内存翻 3 倍（向量存储线性涨 + HNSW 图开销跟涨）；②延迟线性涨（距离计算 O(维度)）；③维度灾难——高维空间稀疏，同 M 下邻居覆盖不足，recall 掉，要保 recall 得加大 M/ef，成本雪上加霜。L05 只算"存储翻 3 倍"是低估。

Q13关于 RRF 融合分数，正确的是？

✓ RRF 无绝对意义，只排序。Q&A 0008：RRF 是"多路排名共识分"（Σ 1/(k+rank)），0.033 不代表 33% 相关——纯粹排序依据。和 cosine（语义相似度）、BM25（字面统计分）本质不同。"够不够"看 Recall@5 ≥ 90%，不看 RRF 分高低。RRF 像 SQL 的 ORDER BY 排序键，Recall 像查全率。

Q14纯 dense Recall@5 = 65%，分析测试集：含错误码/视图名的查询几乎全漏，语义类查询（"慢SQL诊断"）召回正常。第一步改进？

✓ 先开 BGE-M3 一站式。Q&A 0010 升级路径：纯 dense recall 不够 → 先试省事的一站式（BGE-M3 dense+sparse，一个模型一个库），达标就停。不达标（BGE-M3 sparse 对罕见标识符弱）再升双系统。
不是换 3072：维度不解决标识符匹配（embedding 本质边界）；不是调大 K：dense 对标识符排不到前面，K 再大捞不到；不是直接双系统：过度工程，先试轻量的。

Q15为什么 RRF 不能直接把 dense 的 cosine 分数和 BM25 分数相加？

✓ 量纲不同。L06：cosine 范围 [-1,1]，BM25 无上界（能到几十）。直接加：BM25 的 18.3 碾压 cosine 的 0.85 → dense 那路等于没用。所以要么归一化后加权（有调 α 的坑），要么用 RRF 只看排名（量纲无关，主流）。

Q16团队用 GTE-Qwen2 做 dense 检索，发现标识符检索弱要上混合。可行的做法？

✓ 双系统。Q&A 0010：一站式是 BGE-M3 特有福利（一个模型同时出 dense+sparse）。GTE-Qwen2、bge-large-zh 等没有自带 sparse，要混合只能上双系统（dense 模型 + ES BM25）。不是 rerank：rerank 不增加召回，标识符漏召是 recall 问题不是排序问题。

综合 · 跨环节边界与实战

Q17用户问"ORA-01555 怎么处理"，纯向量 RAG 返回了无关的"备份恢复"文档，真正相关的"快照太旧"文档没召回。最可能根因？

✓ 纯向量对精确标识符弱。Q&A 0001/L05：ORA-01555 是无语义标识符，embedding 模型理解不了它和"快照太旧"的语义关联（除非训练语料见过），所以相关文档排不到前面。这是混合检索的根本动机——BM25 字面匹配 ORA-01555 最稳。不是切分/prompt：根因在检索环节对标识符的盲区。

Q18混合检索上线后，Recall@5 从 65% → 88%，但 Precision@5 从 80% → 70%。这说明？

✓ 正常，靠 rerank 补。Q&A 0002：混合检索取两路并集，recall↑（漏的少了），但可能混入更多噪声 precision↓。这正是 L07 rerank 的逻辑——recall 靠混合广召回，precision 靠 rerank 精排。口诀"漏了多捞（混合），杂了精排（rerank）"。recall 88% 接近达标，下一步上 rerank 提 precision。

Q19双系统（dense + ES BM25）架构里，有几个 embedding 模型？BM25 那路跑模型吗？

✓ 1 个 embedding 模型，BM25 不跑模型。Q&A 0009：双系统的"双"指两类检索引擎（向量库 + ES），不是两个 embedding 模型。dense 那路用一个 embedding 模型向量化；BM25 是 ES 内置的 TF-IDF 改进统计算法，直接对原文建倒排索引，不跑任何模型。常见误解：以为双系统要跑两个模型。

Q20运维 RAG POC：5 万篇中文文档，大量错误码/视图名/参数名，要求本地部署。从选型到检索的最佳路径？

✓ 递进升级，评测驱动。综合 L05/L06/Q&A 0010：①本地+中文+标识符多 → BGE-M3（L05）；②先纯 dense 跑基线 Recall@5；③recall 不够 → 开一站式（省事）评测；④一站式不够（sparse 对罕见标识符弱）→ 升双系统（dense + ES 真 BM25）；⑤precision 不够 → 加 rerank（L07）。
不是 OpenAI：数据出境+贵+中文一般；不是直接双系统/3072：过度工程，先试轻量的；不是 3072：BGE-M3 就是 1024，维度不可调，且 3072 代价大（Q&A 0007）。
