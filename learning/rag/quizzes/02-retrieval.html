Q1cross-encoder 比 bi-encoder 精度高的根本原因（L07）

同样是 transformer 模型，为什么 cross-encoder（重排）比 bi-encoder（检索）排序更精？

✓ B。 交互是核心。cross 拼成 [CLS] query [SEP] doc [SEP] 喂 transformer，注意力让 query 每个词直接看 doc 每个词，能学到词级关联——哪怕字面无重叠（ORA-01555 ↔ 快照/回滚段）也能抓到。bi 把 query 和 doc 分别编码成向量，各自编码时看不到对方，只能靠预训练时的语义联想。
为什么不是参数量/训练数据：这是结果不是根因，同参数量下 cross 仍更精，差别在交互。
为什么不是 D：bi 能算 cosine 相关性，只是粗。

Q2rerank 在 RAG pipeline 的位置（L07）

rerank 重排应放在哪一步？

✓ B。 rerank 重排的是检索召回的结果，所以在 retrieve 之后、generate 之前。
为什么不能在检索之前：没召回就没得排，rerank 依赖检索结果。
为什么不在生成之后：rerank 排的是文档不是 LLM 输出。
为什么不能并行：rerank 的输入是检索的输出，有依赖关系，不能同时跑。
完整链路：query → 检索 Top-K1 → rerank Top-K2 → 喂 LLM。

Q3rerank 的成本与延迟（L07）

关于 rerank 的成本与延迟，以下说法正确的是？（呼应"加一跳"）

✓ B。 rerank 只对检索召回的 Top-K1（如 50 个）跑 cross-encoder，不对全库跑，所以延迟可控（bge-reranker-v2-m3 GPU 30-80ms）。但确实加一跳——多一次模型调用，端到端多几十 ms。
为什么不对全库跑（A 错）：cross 不能预计算，全库 5 万篇每对都跑模型要几秒甚至几十秒，所以才用两阶段——bi 粗扫全库、cross 只精排 Top-K1。
为什么不能并行（C 错）：rerank 的输入是检索的输出（Top-K1），有依赖关系，不能同时跑，必然加一跳。
为什么不复用 embedding 模型（D 错）：rerank 模型（cross-encoder）和 embedding 模型（bi-encoder）是两个独立模型，各司其职，rerank 要单独部署、多一份显存。
记忆：rerank = 只跑 Top-K1 + 加一跳 + 独立模型。

Q4诊断：该加什么（综合）

recall@50=92%（够），但 precision@5=50%（Top-5 一半是噪声）。最该加什么？

✓ B 加 rerank。 recall@50=92% 够（相关文档都召回了），问题在排序——bi-encoder 粗排把噪声排进了 Top-5。rerank 精排提 precision，正解。
为什么不是换 embedding：未诊断就换模型是反模式（L02 优化优先级，换 embedding 最贵放最后），且 recall@50 已够说明 embedding 没大问题。
为什么不是调大 K1：recall@50 已够，调大 K1 只多捞噪声，不解决 Top-5 排序问题。
为什么不是加混合检索：混合检索提 recall，本题 recall 已够、缺的是 precision。
口诀：recall 够 precision 不够 → rerank；recall 不够 → 先治检索。

Q5一站式 vs 双系统本质区别（L06）

BGE-M3 一站式混合 和 双系统（dense + ES BM25）的本质区别是？

✓ B。
• 一站式（BGE-M3 特有）：一个模型同时输出 dense + sparse，存一个向量库，一次查询两路都出。省事。
• 双系统：dense 用一个 embedding 模型 + 向量库，BM25 用 ES（独立引擎、倒排索引），两套系统分别查再 RRF 融合。
为什么 A 错：反了——双系统也只有一个 embedding 模型（dense 那路），BM25 是 ES 统计算法不跑模型；一站式也是一个模型。两边 embedding 模型数量都是 1。
为什么 C 错：不一站式一定好——BGE-M3 自带的 sparse 对罕见标识符弱，可能不如双系统里 ES 的真 BM25，所以有"一站式不够再升双系统"的路径（Q&A 0010）。
为什么 D 错：双系统 dense 那路必须有 embedding 模型，只有 BM25 那路不跑模型。
记忆：一站式 = 一模型一库（BGE-M3 福利）；双系统 = 一模型 + ES（两引擎两索引）。

Q6三件套职责对应（综合）

检索三件套 dense / BM25 / rerank 各管什么？

✓ B。 三件套职责不同、互补：
• dense（稠密向量）管语义相似（慢SQL ↔ SQL性能，字面不重叠但语义近）
• BM25（稀疏）管字面精确匹配（ORA-01555、PGXC_STAT_ACTIVITY 这种标识符）
• rerank（cross-encoder）管精排（对召回的 Top-K 重排，提 precision）
为什么 A 错：把 dense 和 BM25 职责搞反了——dense 管语义不管精确，BM25 管精确不管语义。
为什么 C/D 错：三者职责不同，不是都管召回或都管语义。
记忆：dense 管"像不像"、BM25 管"含不含"、rerank 管"准不准"。

Q7K1 和 K2 怎么定（L07）

两阶段检索有 K1（粗召回数）和 K2（精排输出数）。以下说法正确的是？

✓ B。
• K1（粗召回）决定 rerank 的天花板——相关文档没进 Top-K1，rerank 再精也救不回。看 recall@K1 曲线拐点定。
• K2（精排输出）看下游 LLM 上下文窗口和精度需求。
• 经验起步 K1=50、K2=5，按评测调。
为什么不是 K1 越大越好：K1 大 → rerank 慢（要跑更多对）+ 噪声多。
为什么 K1 K2 不必相等：两者独立，K1 管召回广度，K2 管喂 LLM 的量。
为什么 K2 不决定召回上限：召回上限由 K1 定，K2 只决定喂给 LLM 多少。

Q8含 rerank 的优化优先级（综合）

RAG 效果差，recall@50=70%（不够），precision@5=60%。团队提议：①加 rerank ②换 3072 维 embedding ③加混合检索 ④调切分。正确优先级？

✓ B。 recall@50=70% 不够 → 先治检索提 recall，再谈精排：
④ 调切分（廉价，重切文档即可）→ ③ 加混合检索（dense+BM25 互补提 recall）→ recall 上去后，若 precision 不够 → ① 加 rerank（精排提 precision）→ ② 换 embedding 最贵最后。
为什么不能先 rerank（A/D 错）：recall@50 不够，rerank 救不回漏召，先 rerank 是白费。
为什么不能先换 embedding（C 错）：未诊断就换最贵环节，反模式；且 recall 不够的根因可能是切分/检索策略，不一定是 embedding。
口诀：recall 不够先治检索（切分+混合），recall 够了再 rerank 提 precision，换模型永远最后。
