Q1RAG 适用场景（L01）

公司运维知识库每周更新（新故障案例、新版本参数），希望 LLM 能基于最新知识回答。以下哪种方案最合适？

✓ RAG，每周更新知识库。 频繁更新是 RAG 的核心适用场景（L01）。
为什么不微调：每次更新都要重新训练，成本高、周期长，且不能动态更新。
为什么不用长上下文：有 token 上限，且每次调用都把全部知识塞进去，贵且 Lost in the Middle。
为什么不等数据更新：LLM 训练数据有截止日期，等完全不现实。
RAG 只更新知识库，LLM 不动——这是「开卷考试」的本质。

Q2chunk 大小与 overlap（L03）

关于 chunk 大小和 overlap 的设置，以下说法正确的是？

✓ C。 L03 实践值。
为什么不是「chunk 越大越好」：chunk 太大，一个 chunk 含多个主题，向量被「稀释」，召回精确度下降，还占窗口。
为什么不是「overlap 越大越好」：overlap 大能保边界，但冗余增加（同段内容存多份）、重复内容可能多次进 Top-K 挤掉其他相关 chunk。
为什么不是「固定 512」：固定大小会切坏表格、代码块（HugoGu 512 token 表格截断 85%→32% 的踩坑）。必须适配文档类型。
口诀：参数有参考值，但最终靠评测驱动，不拍脑袋。

Q3POC 优化优先级（L02）

团队搭了运维 RAG demo，效果不好。以下优化顺序最合理的是？

✓ B。 L02 的 POC 优化优先级，体现木桶效应和成本意识。
为什么先切分：切分决定上限，改起来廉价（只重切文档，不重训模型），先补最弱且最廉价的板。
为什么混合检索+rerank 第二：提命中，成本中等。
为什么评估第三：评估先行才能量化改进——但这里评估放在优化后是为了先快速见效，实际中评估应尽早搭（L02 提过「评估先行」方法论，POC 里可灵活）。
为什么换模型最后：换 embedding 成本最高（要重新向量化整个知识库），且未必是根因，放最后。
反模式：不诊断就换模型（A/D）、评估最后才搭（A）。

Q4完整检索三层（L04 综合）

一个完整的运维 RAG 检索流程，正确顺序是？

✓ A。 L04 面试视角的「完整检索三层」，顺序不能乱：
① metadata 过滤先圈范围——缩小候选集，省算力、保候选质量（pre-filtering）。
② 混合检索在范围内召回——向量+BM25 互补，提 recall。
③ rerank 最后精排——对召回的 Top-K 重排，提 precision。
为什么 metadata 不能放最后：Top-K 已定，过滤后可能太少甚至空（post-filtering 的坑）。
为什么 rerank 不能放前面：rerank 重排的是召回结果，没召回就没得排。
这三层正交可叠加——一个完整检索 = 圈范围 + 召回 + 精排。

Q5大面积跑偏诊断（环节边界）

用户问「GaussDB 慢 SQL 诊断」，检索 Top-5 返回了 5 个完全不相关的章节（安装部署、备份恢复等），但库里明明有慢 SQL 章节。最可能的问题环节？

✓ embedding 对运维语料理解差。 返回完全不相关 = 大面积跑偏 → 向量化问题（Q&A 0001 口诀：召回大面积跑偏 → 向量化）。
为什么不是切分：切分把章节切碎，至少会召回部分慢 SQL 片段（残缺但相关），不会返回完全不相关的章节。
为什么不是 K 太小：K 小是漏召回（结果太少），不是全错（结果全不相关）。
为什么不是缺 rerank：rerank 解决排序问题，不解决召回问题——召回的都不相关，rerank 排序也排不出相关的。
辨析：如果是「召回 GaussDB 慢SQL 但混了 PostgreSQL 慢SQL」（相关但属性不对）→ 元数据问题；本题是「完全不相关」（大面积跑偏）→ 向量化问题。

Q6切分 + 元数据双问题（环节边界）

用户问「GaussDB 慢 SQL 怎么处理」，返回了只含「现象 + 半个原因」的 chunk（答案残缺），同时 Top-5 里 GaussDB 和 PostgreSQL 的慢 SQL 文档混在一起。这两个问题分别怎么解决？

✓ B。 两个问题根因不同，解法不同——这题考切分和元数据的职责边界：
① 残缺是切分问题（语义完整性）→ 结构化切分按章节切，保证「现象/原因/处理步骤」同 chunk。
② 混召回是元数据问题（结构化属性过滤）→ 加 product 元数据 pre-filter product=GaussDB。
为什么换 embedding 不行：embedding 救不了切分残缺（片段本就残缺），也救不了产品边界（语义相似的结构化属性该用过滤）。
为什么 rerank 不行：能降权 PG 文档，但治标不治本——PG 还占着 Top-K 名额挤掉 GaussDB；更救不了残缺。
为什么增大 K 不行：只多塞噪声，没解决任一根因。
口诀：切分管语义完整性，元数据管结构化属性——别让一个工具干两个活。

Q7pre vs post filtering（L04）

知识库有 product（GaussDB/MySQL）和 version（v8.0/v9.0）元数据。用户问「GaussDB v9.0 参数配置」，团队用 post-filtering（先向量检索 Top-20 再筛 product+version），经常结果太少。最佳改进？

✓ pre-filtering。 L04 重点。post-filtering 的坑：Top-20 里满足 product=GaussDB AND version=v9.0 的可能只有几个，过滤后结果太少甚至空。
为什么 pre-filtering 更好：先把范围缩到 GaussDB v9.0，再在范围内向量检索，召回充足，还省算力（向量检索只在小范围跑）。
为什么不是增大 K：能缓解（多召回些再筛），但成本高（向量检索在大范围跑），且没解决根因——若 GaussDB v9.0 文档本就少，增大 K 也捞不到。
为什么不是 rerank/embedding：这是过滤策略问题，不是召回质量或排序问题，换模型/加 rerank 都不对症。
运维类比：先 WHERE product='GaussDB' AND version='v9.0' 再全文搜，而不是先全文搜 Top-20 再 WHERE 筛。

Q8Recall 优化方向（评估）

评测发现 RAG 系统 Recall@5=40%，Precision@5=80%。这说明什么？该怎么优化？

✓ A。 Recall@5=40% 意味着相关文档只有 40% 进了 Top-5——漏召回严重（答案在库里但没喂给 LLM → 残缺/幻觉）。Precision 80% 说明进去的基本都相关（精度不错）。
优化方向：优先提 recall——增大 K（广召回）、混合检索（向量+BM25 互补提 recall）、调 ANN 参数（ef_search 调大减少近似损失）。
为什么不是「加 rerank」：rerank 提 precision（精度），不提 recall。本题 precision 已经 80%，不缺精度缺召回。
为什么不是「换 embedding」：未诊断根因就换模型是反模式（L02 优化优先级，换模型成本最高放最后）。先试增大 K / 混合检索这些低成本手段。
记忆：recall 低 → 广召回（大 K / 混合检索 / 调 ANN）；precision 低 → 精排（rerank）。
