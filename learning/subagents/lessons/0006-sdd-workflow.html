SDD 工作流（子 agent 驱动开发）

前面 5 课是"会派子 agent"。SDD 是"用子 agent 驱动一整个开发流程"——把计划拆成任务，每个派全新子 agent 实现，实现后过两道 review。这正好是你之前摸到的洞察的正式版：设计留主会话，实现派出去（见 learning-records/0001）。

核心公式

每任务一个全新子 agent + 两阶段 review（先 spec 合规，后代码质量）

主会话当控制器（读计划、派发、答问、整合，不自己写代码）；子 agent 当执行者。

为什么"全新"子 agent

同一个子 agent 干所有任务

任务一的细节堆在上下文里，干任务二时被干扰、串味、越积越乱。

每任务全新子 agent

干净上下文、专注单一任务。前任务不污染后任务——上下文隔离的极致用法。

角色分工

控制器（主会话）读计划、拆任务、派发、答问、整合、不写代码
实现者 implementer实现 + 测试 + 提交 + 自审
spec 审查者查代码是否符合规格（不多不少）
质量审查者查代码质量（好坏）

每个任务的流程

  1. 派 implementer（带完整任务文本 + 上下文，不让它读 plan 文件，直接给全文）
  2. implementer 可能问问题 → 控制器答清楚再让它开工
  3. implementer 实现、测试、提交、自审
  4. 派 spec 审查者 → 查是否符合规格
  5. 派 质量审查者 → 查代码质量
  6. 两道都过 → 标记完成 → 进下一个任务
↻ 循环：spec 或质量审查不过 → implementer 修 → 再审，直到两道都过才进下一任务。全部任务完成后，再派一个 final reviewer 审整体。

两阶段 review 的顺序很重要

✅ 先 spec 后质量

先确认"做对了"（符合规格），再谈"做得好不好"。spec 没过可能要大改，质量先查就白查。

❌ 先质量后 spec

spec 没过就要返工大改，刚查的质量白费。顺序错了浪费 review。

spec 合规：防过度 / 不足建设

spec 审查者不只查"有没有做全"，也查"有没有多做"。

真实案例（Task 2：恢复模式）

spec 审查者发现两个问题：

• 不足：缺进度报告（规格要求"每 100 项报告一次"）

• 过度：多加了个 --json flag（没要求）

→ implementer 去掉 flag、补上进度报告 → spec 审查者再审 → ✅ 通过 → 进质量审查。

关键区分：SDD ≠ 第 5 课的并行

第 5 课 · 并行

多个独立任务，一条消息并发派。无依赖、改不同文件。

SDD · 串行

任务一个接一个，不并行派 implementer——会冲突改同文件，且后续任务常依赖前面。

记法：独立无依赖 → 并行（第 5 课）；有计划有依赖要连续执行 → SDD 串行。

两个实用技巧

① 模型选择（省钱）：机械实现（1-2 文件、规格清晰）用便宜快模型；集成判断用标准模型；架构 / review 用最强模型。

② implementer 四状态：

DONE进入 spec 审查
DONE_WITH_CONCERNS读顾虑，判断是否要先处理
NEEDS_CONTEXT补上下文，重新派发
BLOCKED评估：补上下文 / 换强模型 / 拆小 / 找人

红线（别踩）

  • 不在 main/master 开工（用 worktree）
  • 不跳任何一道 review
  • 不并行派多个 implementer（冲突）
  • 不让子 agent 读 plan 文件——直接给任务全文
  • reviewer 发现问题 → 必须修 + 再审，不跳 re-review
  • spec 没过就开质量审查 → 顺序错
  • 不让 implementer 自审代替正式 review（两者都要）

练一练

测验 1：SDD 每个任务用一个全新子 agent，主要为了避免上下文污染。
测验 2：两阶段 review 的正确顺序是先代码质量、后 spec 合规。
测验 3：SDD 中可以并行派多个 implementer 同时实现多个任务以加速。
测验 4：spec 审查者发现实现多了一个没要求的 flag，这属于"过度建设"，应让 implementer 去掉。
