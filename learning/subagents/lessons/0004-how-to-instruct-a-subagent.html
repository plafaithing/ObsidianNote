怎么给子 agent 一份好指令

上一课你亲手派了一个子 agent。这课把"指令本身"拆开——为什么有些 prompt 派出去要来回返工，有些一次到位。

先记住：子 agent 是"失忆"的

上下文隔离意味着——它看不到你和主会话之前聊过的任何东西，只看得到你这次塞进 prompt 的内容。

所以指令必须"自包含"：像给一个刚入职、什么都不知道的新人写任务单。

单线程时可以含糊

"就那个文件，改一下上次说的"——你们共享上下文，听得懂。

派子 agent 不行

它不知道"那个文件"是哪个、"上次说的"是什么。每个词都得写明白。

自包含 prompt 的四要素

任务 Task
要它干什么（单一、明确、可判定完成）
约束 Constraints
边界（只读/可写、范围、不贴源码、广度）
输出格式 Output
要什么（结构、长度、是否落盘）
上下文 Context
背景（路径、前情、术语）

四个都齐，子 agent 拿到就能独立跑完，不用回来问你。

① 任务——一句话能说清

单一目标、动词开头、能判定"做完了"。

含糊

"看看这个项目"——看什么？看完算完？

明确

"分析 raft1 项目的代码结构与核心功能"——目标清晰。

② 约束——画好边界

约束既是安全栏（别改我文件），也是 token 闸（别读太多）。

无约束

可能改文件、可能 very thorough 读爆 token、可能跑偏看无关东西。

有约束

"只读不改；不贴大段源码；广度 medium；聚焦 src/ 不看 test/"。

③ 输出格式——先说要什么

要什么结构的结果，先讲清；而且要和"任务里问的点"一一对应。

没格式

"随便看看告诉我"——返回一坨散文，不好用。

结构化

"项目概览 / 文件清单 / 启动方式 / 功能伪代码 / 问题清单"——和查询对齐。

要落盘？写明"写入 X 文件"并选可写 agent（如 general-purpose）——Explore 写不了。

④ 上下文——补足它看不到的

它不知道路径、不知道前情、不懂你的缩写术语。

假设它知道

"看那个目录""刚才说的那个 bug"。

写明白

"分析 D:\workplace\code\java\raft1（一个 Raft 共识算法的 Java 实现）"。

实战拆解：你写的 raft1 prompt

第 3 课后你写的这份，其实四要素都齐了，是好 prompt。但有三处可优化：

任务：读取 D:\workplace\code\java\raft1 目录代码
具体查询：1. 当前项目具体是做什么的
          2. 核心功能有哪些，如何实现的
          3. 存在哪些问题
约束：项目只读，不做修改，不贴源代码，必要是可有伪代码
输出格式：项目概览 / 文件清单 / 启动方式 / 功能清单及其实现伪代码
三处可优化
  • ① 没写广度 → token 不可控 （约束要素）
  • ② 查询问了"存在问题"，但输出格式没列"问题清单" → 输出与查询不对齐 （输出格式要素）
  • ③ "存在哪些问题"太宽 → 子 agent 不知从何下手 （任务要素）
广度：medium
任务：分析 D:\workplace\code\java\raft1 目录的代码
具体查询：
  1. 项目是做什么的（一句话 + 关键技术栈）
  2. 核心功能有哪些，各自如何实现（用伪代码）
  3. 存在哪些问题与风险（潜在 bug、并发/一致性、设计缺陷）
约束：只读，不改任何文件；不贴大段源码，必要时用伪代码
输出格式：项目概览 / 文件清单 / 启动方式 / 功能清单(含伪代码) / 问题与风险清单

三个优化正好分别落在约束、输出格式、任务三个要素上——四要素不是死记，是检查清单。

反模式（别这样写）

  • 太含糊："帮我看看代码"
  • 漏约束：没说只读 → 万一派到可写 agent，文件可能被改
  • 输出没格式：返回一坨，没法直接用
  • 假设它知道：用"那个文件""上次说的"
  • 多目标混杂：一个 prompt 塞"读代码+写文档+跑测试" → 拆成多个子 agent

练一练

测验 1：子 agent 能看到你和主会话之前讨论的内容。
测验 2：查询里问了"存在问题"但输出格式没列问题清单——这是输出格式没和任务对齐。
测验 3：一个 prompt 塞了"读代码+写文档+跑测试"三件独立的事，更好的做法是拆成多个子 agent。
